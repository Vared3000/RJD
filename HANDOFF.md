### Суть изменения

Раньше кнопка «Завершить» на открытой задаче дособора незримо создавала и
сразу проводила отдельный документ Выдачи (`tasksService.complete` →
`issuanceService.createAndPostForTask`) — без черновика, без возможности
проверить состав. Теперь кладовщик на странице «Задачи на доукомплектовку»
выбирает открытые задачи одного работника и одного склада (по умолчанию все,
можно снять отдельные галочкой) и жмёт **«Оформить довыдачу»** — создаётся
обычный черновик Выдачи (позиции с одинаковой моделью/размером/ростом
объединяются в одну строку с суммарным количеством). Дальше — полностью
штатный редактор выдачи: можно уменьшить количество, добавить/удалить
строки, проверить дату и ответственного, провести штатной кнопкой
«Провести». Задачи закрываются только по факту успешного проведения —
частично или полностью — и связанный документ виден в общем списке выдач,
участвует в отчётах и печатных формах, а на его странице доступна кнопка
«Сохранная расписка» (уже существующий модуль `print-forms/preservation-
receipt` — принимает `issuanceId`, ничего в нём менять не потребовалось,
подтверждено чтением кода и существующим тестом до начала работы).

### Модель данных

- Миграция `0078-issuance-task-fulfillments.js`: `issuance_tasks` получил
  `draft_document_id` (nullable FK на `issuance_documents`, RESTRICT) —
  указатель «сейчас в оформлении в этом черновике», обнуляется при
  проведении/удалении черновика в обе стороны (задача закрыта или
  переоткрыта). Новая таблица `issuance_task_fulfillments` (`task_id`,
  `document_id`, `quantity`, `created_at`, без `updated_at` — неизменяемый
  журнал) — история «какой документ сколько закрыл по этой задаче»: одна
  задача может закрываться несколькими документами со временем (частичная
  довыдача, затем ещё одна довыдача на остаток), что не пережило бы старое
  единственное поле `fulfilling_document_id` — оно удалено (данные
  перенесены бэкофиллом в новую таблицу перед удалением колонки, на случай
  уже существующих `completed`-задач в БД). `ISSUANCE_TASK_STATUSES`
  расширен до `open`/`in_progress`/`completed` (без DB CHECK — по конвенции
  проекта). `cancelled` из рекомендованного в ТЗ набора статусов сознательно
  не заведён — ТЗ прямо разрешает опустить его в первом релизе без явной
  команды отмены.
- **Ключевое архитектурное решение**: `IssuanceTask.quantity` мутируется на
  месте (уменьшается при частичном закрытии), а не остаётся историческим
  числом — тот же приём, что уже применяется к `IssuanceLine.quantity` в
  `applyIssuanceSideEffects`. Остаток «обновляет исходную потребность» (один
  из двух вариантов, явно разрешённых формулировкой ТЗ «либо…либо»), а не
  создаёт связанную дочернюю задачу — проще, без колонки `parentTaskId`.

### Backend

- `server/src/modules/issuance/tasks/` — `tasksService.createDraft({taskIds,
  userId})` заменил `complete()`: транзакция, лочит все выбранные задачи
  (`FOR UPDATE`, сортировка по id против дедлоков), проверяет `status===
  'open'` (иначе 409 — защита от двойного клика/двух пользователей),
  проверяет единственность работника и склада (иначе 400), группирует по
  `(modelId,sizeId,heightSizeId)`, создаёт обычный черновик через
  `issuanceRepository` напрямую (`tasksService` больше не импортирует
  `issuance.service.js` — зависимость стала однонаправленной). Новый роут
  `POST /issuance/tasks/create-draft`, `tasks.validation.js` (`zod`,
  раньше файла не было). `tasksRepository` — новые методы
  `findManyLocked`/`findByDraftDocument`/`markInProgress`/`releaseToOpen`/
  `updateProgress`/`createFulfillments`/`findFulfillmentsByDocument`/
  `deleteFulfillmentsByDocument`, экспортирует `issuanceTaskKey()` —
  переиспользуется в `issuance.service.js`.
- `server/src/modules/issuance/documents/issuance.service.js` — новая
  функция `reconcileTaskFulfillments()` (сопоставляет задачи с фактически
  выданным по их ключу, распределяет FIFO — задачи старше закрываются
  первыми — между несколькими задачами одного ключа, если довыдача объединила
  несколько задач с одинаковой моделью/размером/ростом), переиспользуется в
  `post()` и `revise()`:
  - `post()` — после существующего частичного проведения (`tolerateShortage:
    true`) ищет задачи, связанные с этим документом (`draftDocumentId`),
    реконсилирует их и **фильтрует** сгенерированные `shortages` по
    обработанным ключам ПЕРЕД generic-созданием orphan-задач — без этого
    нехватка по строке довыдачи создавала бы одновременно и переоткрытую
    исходную задачу, и новую задачу-дубль на тот же дефицит (прямо
    запрещённый ТЗ сценарий).
  - `remove()` — при удалении черновика находит связанные задачи и
    возвращает их в `open`.
  - `revise()` — сложнее: правка уже проведённой довыдачи должна не
    «сломать» статус задачи. Перед обычной логикой revise находит
    исторические `issuance_task_fulfillments` этого документа, реверсирует
    их (`quantity` задачи возвращается, статус — `open`), удаляет старые
    fulfillment-записи; после применения новых строк (`tolerateShortage`
    остаётся `false`, как и раньше для revise — значит либо полный успех,
    либо `400` до коммита, реверс тоже откатится) заново прогоняет ту же
    `reconcileTaskFulfillments()` по свежим данным. Покрыто тестом (см.
    ниже) — уменьшение количества в уже проведённой довыдаче корректно
    возвращает часть потребности в `open` без задвоения истории.
  - `createAndPostForTask()` удалена целиком — заменена явным
    черновиком+штатным `post()`.

### Найденные и исправленные дефекты этой сессии (в тестах, не в продакшн-коде)

1. **`post()` целиком отклоняет документ, если доступного остатка нет вообще
   ни по одной строке** (существующее, документированное поведение) — черновой
   набросок теста наивно предполагал, что `createShortageTask` с нулевым
   остатком создаст задачу; на деле нужен хотя бы частичный остаток (`>0`, но
   `<` запрошенного). Фикс — вынесен отдельный `receiveStock()`-хелпер,
   `createShortageTask({available, requested})` явно принимает оба числа.
2. **Cохранная расписка требует `employee.dpoId`** (`preservation-
   receipt.context.js` — `ApiError.badRequest`, если у работника нет ДПО) —
   фикстура теста изначально не создавала ДПО. Добавлено создание ДПО с
   минимальными реквизитами (по образцу `print-forms-fixture.js`) и
   `dpoId` в создании работника.
3. **Порядок очистки тестовых данных для сценария «два склада одной
   организации»**: цикл удалял `Organization` по первому `unique` ДО того,
   как второй `Warehouse` (созданный на той же организации, но с ДРУГИМ
   `unique`-именем) был удалён — `RESTRICT` на `warehouses_organization_id_
   fkey`. Исправлено на два прохода: сначала все зависимые сущности (склады,
   работники, номенклатура, размеры, поставщики) по всем `unique`, затем
   организации и ДПО.

### Найденные и исправленные дефекты этой сессии

1. **Реальный дефект сервиса: работник без даты приёма выпадал из отчёта
   при фильтре по конкретному ДПО.** Хук `employees.service.js#mutationHooks
   .afterCreate` создаёт `EmployeeDpoAssignment.validFrom = hireDate ??
   сегодняшняя дата` — если `hireDate` не указан, единственное назначение
   работника датируется РЕАЛЬНОЙ датой создания записи, а не историческим
   периодом отчёта. Исходный запрос в `turnover.service.js` фильтровал
   назначения условием `validFrom <= toDate`, поэтому при запросе отчёта за
   прошлый период (например, март 2026, пока реальная дата — август 2026)
   единственное назначение такого работника (`validFrom` = август) вообще не
   попадало в выборку. `buildAssignmentLookup` возвращал `null` для всех дат
   периода → `passesDpoFilter` (при фильтре по конкретному ДПО) отбрасывал
   работника целиком, хотя ТЗ прямо требует: «работник без даты приёма может
   входить в численность». Именно на этом падал автотест сценария №3
   («неполная карточка») из ТЗ — `Cannot read properties of undefined
   (reading 'start')`, так как отчёт возвращал 0 строк.
   Исправлено двумя правками в `turnover.service.js`:
   - Запрос `EmployeeDpoAssignment.findAll` больше не фильтрует по
     `validFrom`/`validTo` — тянутся все назначения работника целиком (список
     работников уже ограничен фильтрами отчёта, лишних строк на сотрудника
     обычно 1-3, нагрузка не проблема для отчётного эндпоинта).
   - `buildAssignmentLookup(assignments)` получил фолбэк: если дата раньше
     самого раннего известного назначения — работник экстраполируется в ДПО
     этого самого раннего назначения (а не считается «без ДПО»), как
     наиболее разумная трактовка отсутствия истории раньше даты создания
     карточки.
2. **Дефект теста (не сервиса): проверка `formulaText` требовала ОТСУТСТВИЯ
   слова «текучесть».** ТЗ прямо требует явно объяснить в тексте формулы,
   ПОЧЕМУ это не текучесть («причины увольнения система не хранит») — это
   неизбежно означает упоминание самого слова в тексте-предупреждении.
   Утверждение `formulaText.includes('текучест') === false` в тесте
   противоречило этому требованию и падало на реальном (корректном) тексте
   сервиса. Заменено на позитивную проверку наличия обязательной оговорки
   (`/не показатель текучести/`) — то, что показатель НИГДЕ не называется
   «текучестью» как метрикой, отдельно проверяют точные заголовки колонок
   Excel («Сменяемость, %» / «Оборот кадров, %», не «Текучесть, %»).
3. **Дефект теста: `sheet.actualRowCount` после записи+чтения `.xlsx` через
   ExcelJS недооценивает количество строк на 1** (не подхватывает последнюю
   добавленную строку — воспроизведено отдельным минимальным скриптом
   напрямую через `generateTabularExcel()`: `rowCount` вернул 6,
   `actualRowCount` — 5, хотя обе строки данных и итога реально записаны и
   читаются по номеру). Тест ошибочно ловил строку данных вместо итоговой
   (`totalRow.getCell(1).value` возвращало имя ДПО вместо `'Итого'`).
   Исправлено — обе проверки (`headerRowNumber`, `totalRow`) теперь используют
   `sheet.rowCount`, а не `sheet.actualRowCount`. Сам `tabular-document.js`
   не менялся — дефект был только в тесте; **держать в голове на будущее**:
   в новых тестах, читающих сгенерированный Excel через
   `workbook.xlsx.load()`, использовать `rowCount`, не `actualRowCount`, для
   поиска последней записанной строки.

### Грабли этой сессии — держать в голове при следующей правке `employees.repository.js` или похожей сортировки по вычисляемому полю

- **`findAndCountAll` с `limit`+`hasMany`-инклюдом (`EmployeeMeasurement`)
  заставляет Sequelize оборачивать запрос в подзапрос** — сырой SQL-литерал
  (`sequelize.literal('CASE WHEN "Alias"."col" ...')`) в `order` после этого
  не резолвится ни с одним разумным вариантом алиаса корневой таблицы:
  пробовал `"Employee"` (имя модели) → `столбец Employee.archived_at не
  существует`; `"employees"` (имя таблицы) → `в элементе предложения FROM
  неверная ссылка на таблицу "employees"`. Оба диагностированы не гаданием, а
  прямыми `curl`-запросами к живому dev-серверу (`node --watch` уже
  перезагружен). **Решение — не использовать сырой SQL для сортировки по
  вычисляемому полю в запросе с пагинацией+hasMany**: `archivedAt`/
  `terminationDate` дают ту же сортировку через обычные колонки, если
  подобрать `NULLS FIRST`/`NULLS LAST` под смысл (см. следующий пункт) —
  Sequelize сам корректно резолвит обычные `[[col, dir]]` внутри подзапроса,
  проблема была именно в `literal()`.
- **Направление `NULLS FIRST`/`NULLS LAST` — не «очевидное».** Когда `NULL`
  означает *более ранний* статус (ещё не уволен/не архивирован), для ASC
  нужен `NULLS FIRST`, а не `NULLS LAST` — Postgres по умолчанию считает NULL
  «больше любого значения» (что даёт NULLS LAST по умолчанию при ASC), это
  обратно тому, что нужно, если NULL — это «меньший» статус. Первая версия
  (`NULLS LAST` для обоих направлений) прошла лайв-проверку `sort=status`
  без 500-ошибки, но дала **обратный порядок** (уволенные раньше активных) —
  поймано интеграционным тестом (`assert.deepEqual` на порядке id), не
  проверкой на глаз. Исправлено: `dir === 'ASC' ? 'NULLS FIRST' : 'NULLS
  LAST'` для обеих колонок (`archivedAt`, `terminationDate`).
- **Фильтр по региону нельзя реализовать через `where`+`required: true` на
  `include: { model: Dpo, as: 'dpo' }`** в этом же запросе (та же причина —
  subQuery-обёртка `findAndCountAll` из-за `EmployeeMeasurement`) — падало с
  `таблица "dpo" отсутствует в предложении FROM`. Рабочее решение — два
  простых запроса: сперва `Dpo.findAll({ where: { region } })` → список
  `id`, затем `where.dpoId = { [Op.in]: ids }` (пересечь с `filters.dpoId`,
  если оба фильтра заданы одновременно) — никакой JOIN-фильтрации, только
  простое условие на собственной колонке `Employee.dpoId`. Тот же приём
  применён в `reportsRepository.findEmployeesForPersonnelList` для
  единообразия (хотя там `findAll` без пагинации/лимита и риска подзапроса
  не было — сделано ради одного способа фильтрации в обоих местах, не два
  разных).
- **`applyEmployeeStatusFilter` (статус «Активен» через `where[Op.or]`) и
  фильтр поиска по ФИО/табельному (тоже через `where[Op.or]`) конкурируют за
  один и тот же ключ объекта** — если оба одновременно активны, второй
  вызов молча стирает первый (JS object key collision, не ошибка на уровне
  Sequelize/Postgres — проявляется только как неверная выборка). Код-ревью не поймал бы это без явного теста на комбинацию (`search` + `status=active`
  вместе) — добавлен именно такой тест. Исправлено через общий
  `addOrGroup(where, orClauses)` — копит все OR-группы в `where[Op.and]`
  массивом вместо перезаписи `where[Op.or]`.
- **Общий приём диагностики для будущих похожих багов**: `node --watch` уже
  держит dev-сервер (backend :4000) перезапущенным на каждое сохранение
  файла — прямой `curl` с реальным токеном к живому dev-серверу на реальных
  2552 работниках оказался быстрее и точнее, чем гонять полный
  `pnpm --filter @workwear/server test` (~5 минут) на каждую гипотезу об
  SQL-ошибке. Полный прогон нужен только для финального подтверждения, не
  для итеративной отладки одного запроса.

### Грабли этой сессии — держать в голове при следующей правке SQL/тестов

- **Sequelize именованные `replacements` не сериализуют JS-массив в
  Postgres-литерал массива.** `ANY(:instanceIds::uuid[])` в сыром
  `sequelize.query()` давал невалидный SQL (Postgres пытался распарсить
  единственный UUID как литерал массива). Правильный паттерн для «список
  значений» в сыром запросе — `IN (:instanceIds)`, не `ANY(...::type[])`.
- **`node:test` выполняет `t.after()`-хуки в порядке РЕГИСТРАЦИИ, не в
  обратном.** Если хук для дочерней сущности (документ) регистрируется
  ПОСЛЕ хука для родительской (сотрудник/склад, на которую документ
  ссылается по FK `RESTRICT`), очистка падает с ограничением внешнего
  ключа. Правило: собирать ID для очистки в `state`-объект ДО регистрации
  фактического `t.after()`, чтобы был только один хук на тест с заведомо
  верным FK-порядком внутри.
- **Оба класса багов сначала проявились не как явная ошибка, а как
  зависание всего прогона** (`pnpm --filter @workwear/server test` висел
  без вывода — `Select-Object -Last N` в PowerShell буферизует весь поток
  и не отдаёт ничего, пока процесс не завершится, поэтому зависший дочерний
  процесс выглядел как «тишина», не как ошибка). Диагностика: (1)
  `pg_stat_activity`/`pg_locks` — ноль реальных запросов/блокировок,
  значит не блокировка БД; (2) `Get-CimInstance Win32_Process` с
  `ParentProcessId` — нашёл, что `node --test` создаёт ОТДЕЛЬНЫЙ дочерний
  процесс НА КАЖДЫЙ файл теста, и именно один конкретный файл
  (`issuance-revise.test.js`) не завершался, хотя все его подключения к
  Postgres уже закрылись; (3) прогон проблемного файла в изоляции с жёстким
  таймаутом (`child.kill('SIGKILL')` через `setTimeout`) — показал реальные
  TAP-результаты и точную причину. Полезный общий приём на будущее: если
  `pnpm test` «висит без вывода», не считать это гарантированной
  блокировкой БД — сначала проверить `pg_stat_activity`, затем
  `Get-CimInstance Win32_Process -Filter "Name='node.exe'"` для поиска
  зависшего дочернего процесса по `ParentProcessId`.
- Длина `unique`-строк в тестовых фикстурах: `Size.value` ограничен 32
  символами (`size.validation.js`) — при склейке длинного префикса с

пересидевать не пришлось, баг был только в чтении, не в записи.

### Второй найденный баг — allow-list в `template-safety.js` отклонял абсолютно любой файл

`inspectUploadSafety()` (allow-list записей zip-архива `.xlsx`, написан в
прошлой сессии, но ещё не был подключён ни к какому вызывающему коду) не
пропускал через свой regex-список **служебные записи-папки** zip-архива
(`_rels/`, `xl/`, `xl/_rels/`, `xl/worksheets/`, `xl/theme/`, `docProps/` —
`adm-zip` перечисляет их как отдельные entries с `entry.isDirectory === true`
наравне с файлами). Поскольку эти записи есть в **любом** валидном `.xlsx`
(в т.ч. в самом сидированном бандл-шаблоне), первая же реальная загрузка
отклонялась бы с сообщением «Запись архива не разрешена» на собственных
папках архива. Фикс — пропускать `entry.isDirectory` записи в цикле проверки
до сравнения с allow-list. Без этого фикса вся фича загрузки была бы
нерабочей независимо от корректности макета.

## Текущий статус (31.07.2026, Этап 12)

Реализованы пять обязательных печатных форм: ФПУ-26, приложение 1.5,
приложение 1.7, личная карточка работника и УПД. Первые четыре доступны в

приоритет, а при их отсутствии модуль читает нормализованные строки архива

строк, заполняют реквизиты всех 15 ДПО, разбирают 27 архивных личных карточек
на работников, размеры, 338 строк номенклатуры, нормы, сроки использования и
даты выдачи/возврата, а также 18 строк исходного УПД. В исходных данных ошибок
разбора нет. Реальный УПД № 172 за 31.07.2026 воспроизводит двухстраничную

## Локальное окружение — важные отличия от "стандартного" сетапа

- **Docker не установлен** на этой машине. `docker-compose.yml` написан и
  предназначен для сервера предприятия (раздел 4 ТЗ — развёртывание без
  интернета), но локальная разработка идёт напрямую против локального
  PostgreSQL 18 (Windows-сервис `postgresql-x64-18`, уже запущен).
- БД `workwear_erp`, роль `workwear_app` / пароль `workwear_app_password` —
  создана отдельно от суперпользователя, не пересекается с базой `cleanflow`
  соседнего (чужого) проекта на этой же машине.
- `.env` в корне уже заполнен рабочими значениями (скопирован из
  `.env.example`), включая `BOOTSTRAP_ADMIN_PASSWORD=change-me-on-first-login`
  для входа как `admin`.
- Git Bash на Windows ломает кириллицу в inline-аргументах к нативным
  .exe (`curl -d '{"name":"Русский текст"}'`, `psql -c "... WHERE x = 'рус'"`)
  — байты манглятся при передаче argv в дочерний процесс. Для тестовых
  запросов с кириллицей писать payload в файл и передавать через
  `curl --data-binary @file.json` / `psql -f file.sql`, либо гонять кириллицу
  только через stdin (пайпы это не ломает), либо просто использовать
  латинские тестовые имена (`pwwhdocs<timestamp>` и т.п.) — так делали
  Playwright-проверки в нескольких сессиях подряд. Сами данные в БД/
  приложении не повреждаются — проблема только в этом одном инструменте
  тестирования.
- Инструменты Read/Write/Edit иногда не видят файл, который только что сами
  создали в этой же кириллической папке (`2-этаж Ржд`) — ошибка "File does
  not exist" сразу после успешного создания, притом что повторный вызов того
  же инструмента с тем же путём затем срабатывает. Природа не установлена
  окончательно (подозрение на рассинхронизацию с OneDrive, который часто
  делает Known Folder Move для `Desktop` на Windows, либо на путаницу
  Unicode-эквивалентных форм написания кириллицы при повторном наборе пути
  моделью) — не является багом кода проекта. Что помогает: (1) для новых
  файлов использовать `cat > relative/path <<'EOF' ... EOF` через Bash с
  относительным путём (без кириллицы вообще, если `cd` в корень проекта уже
  выполнен) — надёжнее, чем Write/Edit с абсолютным путём; (2) для правки
  существующих файлов — `perl -0pi -e` или `sed` через Bash вместо Edit;
  (3) если Read/Write/Edit всё же нужны — просто повторить вызов, обычно
  срабатывает со второго раза; (4) после Bash-правок всегда проверять
  `cat`/`grep` результат — не доверять только сообщению об успехе.

   `getByRole('button', { name, exact: true })` (`getByText` ловит и текст
   заголовка модалки — strict mode violation), поля `EntityFormModal`/
   `CatalogFormField` — `#<fieldName>` (id совпадает с `name`, в т.ч. у
   `Select` через `Controller`). Контролируемые чекбоксы без optimistic
   update — `.click()` + `waitForTimeout`, не `.check()` (см. Этап 10).
   Оправдало себя во всех сессиях подряд, где применялось.
3. После ручных проверок — чистить тестовые данные из dev-БД (порядок с
   учётом FK — см. `docs/architecture.md` "Тесты, создающие данные" и
   `t.after()` в тестовых файлах), чтобы не путать реальные данные с
   мусором на следующей сессии.
4. `pnpm lint` (корневой ESLint) и `pnpm --filter @workwear/client build`
   (`vite build`) — быстрая проверка компиляции клиента без запуска dev-сервера.

## Где искать паттерны и грабли

`docs/architecture.md` — обязателен к прочтению перед новым модулем:
Controller/Service/Repository, конвенции БД (UUID, snake_case, soft-delete
через `archivedAt`), `CatalogPage`/`EntityFormModal` и их грабли
(`field.defaultValue`, `valueAsNumber`), паттерн документов
(шапка+строки+проведение, блокировка транзакции, `StockMovement`), порядок
очистки тестовых данных.

`server/src/modules/purchases/receiving/` — самый полный пример
draft/posted документа: routes → controller → service (транзакция
проведения) → repository, плюс zod-валидация с `preprocess` для
опциональных UUID/чисел. `server/src/modules/transfers/` — ещё один
draft/posted пример (движение на оба склада).

`server/src/modules/service-documents/` — пример двухфазного документа
(draft/sent/completed) и того, когда оправдано выносить общую фабрику для
двух похожих документов (Стирка/Ремонт), а не дублировать модуль целиком.

`server/src/modules/inventory/` — пример документа, который сознательно НЕ
меняет остатки склада (сверка, а не складская операция) — если понадобится
что-то подобное (например, черновой отчёт с последующим утверждением),
можно ориентироваться на этот паттерн (снимок при создании + подтверждение
построчно + завершение без побочных эффектов).

`server/src/modules/admin/` — пример модуля с явным журналом событий вместо
generic-diff (сравни с `dpo/`) и переиспользования `createCatalogHooks` для
select-опций с нестандартным (не корневым) REST-путём (`admin/roles`).
Полезно свериться с ним, если понадобится ещё один модуль с построчными
действиями сверх обычной архивации (см. `AdminUsersPage.jsx`, не через
`CatalogPage`).

`server/src/modules/adjustments/` — пример draft/posted документа с
несколькими типами строк в одной таблице (`adjustmentType`: дискриминированный
zod-union вместо 4 отдельных модулей), где каждый тип по-разному действует на
экземпляр при проведении. На фронтенде — одна форма-в-модалке с полями,
скрываемыми через `hiddenWhen` по выбранному типу
(`client/src/features/adjustments/model/line-schema.js`), а не отдельная
модалка на тип.

`server/src/modules/dpo/` — пример модуля с историей изменений (снимок
старых значений изменившихся полей + diff между соседними записями в
сервисе, не во фронтенде) и с поиском (ILIKE через `Op.or` в репозитории).
`server/src/modules/reports/` — пример read-only агрегирующего модуля без
собственных моделей (routes→controller→service→repository, переиспользует
существующие сервисы типа `stock.service.js`, а не дублирует их логику);
`coverage.service.js` там же реконструирует историю владения для расчёта
периодического обеспечения. Для пользовательского аудита жизненного цикла
теперь существует отдельная таблица `instance_events` и API
`GET /api/v1/instances/:id/history`; запись события встроена в транзакции
всех документов, меняющих экземпляр.
