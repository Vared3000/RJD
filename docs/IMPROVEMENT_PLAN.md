# План доработки ERP «Учёт спецодежды»

Дата создания: 2026-08-08
Назначение: единый рабочий план для продолжения разработки в разных сессиях и разными моделями.
Целевая эксплуатация: сервер внутри одной локальной сети предприятия, без публичного интернет-доступа.

## Как пользоваться планом

- Перед началом любой задачи прочитать `CLAUDE.md`, `HANDOFF.md` и
  `docs/architecture.md`.
- Проверить `git status` и не перезаписывать чужие незакоммиченные изменения.
- Выполнять только одну задачу плана за раз.
- Не смешивать независимые задачи в одном коммите.
- Перед миграциями проверить состояние dev-БД и сделать резервную копию, если
  изменение затрагивает существующие данные.
- Уже применённые или опубликованные миграции не редактировать. Создавать
  следующую миграцию, кроме ещё не опубликованной активной миграции текущей
  задачи.
- Бизнес-операцию, изменение экземпляра, движения и запись истории выполнять
  в одной транзакции.
- После завершения задачи обновить этот файл, `README.md` и `HANDOFF.md`.

Обязательные проверки после каждой задачи:

```powershell
pnpm.cmd lint
pnpm.cmd format:check
pnpm.cmd --filter @workwear/server test
pnpm.cmd --filter @workwear/client build
```

Если тестовая инфраструктура ещё не изолирована от dev-БД, перед запуском
backend-тестов проверить правила очистки из `docs/architecture.md`.

## Задача 4. Защитить документы от одновременной правки

Статус: **Готово** (2026-08-08).

### Цель

Проведённый документ всегда соответствует созданным движениям и изменениям
экземпляров.

### Охват

- поступление;
- выдача;
- возврат;
- перемещение;
- списание;
- инвентаризация;
- стирка;
- ремонт.

### Работы

- [x] Добавление, изменение и удаление строки выполнять в транзакции.
- [x] Блокировать шапку документа через `SELECT ... FOR UPDATE`.
- [x] После блокировки повторно проверять статус.
- [x] Не позволять изменять строки после начала проведения.
- [x] Рассмотреть поле `version` для optimistic locking.
- [x] Возвращать `409 Conflict` при конфликте конкурентных изменений.

### Тесты

Параллельно отправлять проведение и изменение строки. Допустим только один
непротиворечивый результат; проведённый документ должен совпадать с движениями.

### Результат четвёртого релиза

- Поступление, выдача, возврат, перемещение, списание, инвентаризация, стирка и
  ремонт используют одну блокировку шапки для правок и смены статуса.
- Правка шапки, добавление, изменение, удаление строки и автозаполнение
  комплекта выполняются в транзакции после `SELECT ... FOR UPDATE`.
- После ожидания блокировки статус читается повторно; проведённый, отправленный
  или завершённый документ возвращает `409 Conflict`.
- Проведение читает строки в той же транзакции после блокировки шапки, поэтому
  движения и изменения экземпляров соответствуют зафиксированному документу.
- Для инвентаризации создание шапки и снимка строк дополнительно объединено в
  одну транзакцию.
- Поле `version` не добавлялось: пессимистическая блокировка покрывает все
  серверные мутации документов и не требует изменения клиентского контракта.
- Конкурентный тест «проведение против правки строки» подтверждает: проведение
  создаёт 3 экземпляра и 3 движения, запоздавшая правка получает `409`.
- Полный изолированный прогон: 18/18 тестов.

### Правило отбора

В акт включать экземпляр, если период владения им пересекается с выбранным

```text

дата возврата отсутствует или дата возврата >= первый день месяца
```

Поэтому вещь, выданная в предыдущем месяце и не возвращённая до начала
следующего, должна присутствовать в каждом соответствующем ежемесячном акте.
Одежда, выданная и возвращённая внутри месяца, также включается с фактическим
интервалом владения.

существующей серверной модели:

1. Новый `GET` эндпоинт в `print-forms/templates` разбирает выбранную версию
   через `exceljs` (переиспользуя `template-markers.js`) и отдаёт JSON-слепок:
   ячейки, объединения, стили, ширины/высоты, параметры страницы, известные
   маркеры на своих местах.
2. Фронтенд рендерит этот JSON как HTML-таблицу с своим (не сторонним)
   выделением ячеек/диапазонов, панелью стилей и палитрой разрешённых
   маркеров (`fpu26MarkerSpec` уже описывает допустимый набор).
3. «Сохранить версию» отправляет отредактированный JSON на новый `POST`,
   который **тем же `exceljs`** собирает реальный `.xlsx` из слепка и
   прогоняет его через уже существующий `printFormTemplatesService` —
   валидация, безопасность, пробная генерация и версионирование не
   дублируются, только новый способ получить входной буфер (сборка из JSON
   вместо разбора загруженного файла).

Дать пользователю зафиксировать порядок работ по крайней мере на 3-4
итерации перед стартом (grid-компонент → панель стилей → маркеры/объединения
→ параметры страницы), т.к. это отдельная многофайловая архитектурная задача,
а не точечная правка.

### Тесты

- [ ] Изменение ширины столбца и высоты строки сохраняется в Excel и PDF.
- [ ] Перенос текста и объединения не ломаются при 0, 1 и 100 строках акта.

Администратор может скачать шаблон, выровнять и оформить его в Excel,

## Задача 22. Редактирование проведённых поступлений и выдач

Статус: **Готово 11.08.2026**.

### Цель

Разрешить уполномоченному пользователю исправить поздно обнаруженную ошибку в
проведённом поступлении или выдаче без ручного изменения экземпляров, остатков,
движений и истории.

Для пользователя это одна команда «Редактировать проведённый документ», но на
сервере выполняется контролируемое перепроведение, а не прямая правка строк.

### Бизнес-процесс

1. Пользователь открывает проведённый документ и нажимает «Редактировать».
2. Система показывает предупреждение и проверяет последующие операции по всем
   затронутым экземплярам.
3. Безопасные изменения выполняются в одной транзакции: блокировка документа и
   экземпляров, отмена старых эффектов, сохранение новых данных, повторная
   валидация и проведение новой редакции.
4. Номер документа сохраняется, номер редакции увеличивается.
5. В журнале остаются пользователь, время и снимки данных до и после изменения.
   Причина может быть указана, но не является обязательной.

### Ограничения целостности

- [x] Нельзя удалить или изменить поступивший экземпляр, если по нему уже есть
  выдача, возврат, перемещение, стирка, ремонт, списание или инвентаризация.
- [x] Нельзя заменить экземпляр или работника в выдаче, если после неё уже есть
  возврат либо иная последующая операция по экземпляру.
- [x] Разрешённые независимо от движений поля (например, примечание) меняются
  без отмены складских эффектов, но также попадают в историю редакций. —
  реализовано как сознательное упрощение подтверждённого решения №1 (см.
  результат ниже): отдельного облегчённого пути нет, правка любого поля идёт
  через единый always-full `revise()`; итоговое поведение («поле меняется,
  попадает в историю») от этого не отличается для пользователя.
- [x] При конфликте система перечисляет зависимые документы и объясняет, какие
  из них нужно отменить начиная с самого позднего.
- [x] Параллельная правка защищена блокировкой; второй пользователь получает
  `409 Conflict`, а не перезаписывает изменения. Отдельного optimistic-lock
  `version`-поля нет (решение задачи 4 не пересматривалось) — конкурентность
  закрыта пессимistической блокировкой шапки, `revisionNumber` служит только
  человекочитаемым номером редакции для аудита.

### Связь с актами

- [x] Изменение даты, работника, ДПО, состава или цены выдачи помечает
  затронутые месячные акты как требующие пересчёта.
- [x] Уже зафиксированный акт не меняется молча.
- [ ] Повторную фиксацию выполняет администратор по правилам задачи 24 — сама
  задача 24 (пересчёт/версии актов) не начата, здесь только маркер `isStale`.

### Тесты и критерий готовности

- [x] Проведённое поступление без зависимостей успешно меняет шапку и строки;
  старые партия, экземпляры и движения не остаются дублями.
- [x] Проведённая выдача без последующих операций успешно меняет работника,
  дату, склад и состав; имущество обоих работников и остатки корректны.
- [x] Зависимый документ блокирует опасное изменение с понятным сообщением.
- [x] Ошибка в середине перепроведения откатывает всю транзакцию.
- [x] До и после перепроведения сумма движений и состояния экземпляров согласованы.

  Postgres-литерал массива для `::uuid[]`-каста, получался невалидный
  синтаксис; заменено на `instance_id IN (:instanceIds)` — Sequelize
  корректно раскрывает массив в списке для `IN`. (2) В новых тестовых
  файлах `unique`-строки вида `Test IssRevise Rollback ${Date.now()}`
  превышали лимит `Size.value` в 32 символа (провал создания размера,
  затем весь тест падал на `size.body.data.id`), и в двух тестах
  «редакция черновика отклоняется» `t.after()` для дочернего документа
  регистрировался ПОСЛЕ хука для родительской сущности (сотрудник/склад) —
  node:test выполняет `after`-хуки в порядке регистрации (не в обратном),
  поэтому FK-очистка шла в неверном порядке и падала с `RESTRICT`.
  Оба класса багов сначала проявились как зависание всего прогона
  (`pnpm --filter @workwear/server test`) на файле `issuance-revise.test.js`
  без вывода — диагностировано через `pg_stat_activity`/`pg_locks` (не
  нашли ни одного зависшего запроса — значит не блокировка БД) и через
  `Get-CimInstance Win32_Process` с `ParentProcessId` (нашёл, что именно
  дочерний процесс `node --test src/tests/issuance-revise.test.js` не
  завершался, хотя все его подключения к Postgres уже закрылись), затем
  подтверждено прогоном файла в изоляции с жёстким таймаутом.
- Проверено: `pnpm --filter @workwear/server test` — 52/52 (было 42, +10
  новых тестов в `receiving-revise.test.js`/`issuance-revise.test.js`),

  чисто. Живая проверка Playwright на dev-сервере (после `pnpm db:migrate`
  для миграций `0067`–`0069`): редактирование проведённого Поступления
  (смена цены строки) — тост об успехе, бейдж «Проведён · Редакция №2 ·
  изменил: Администратор системы», партия не задублирована; блокировка
