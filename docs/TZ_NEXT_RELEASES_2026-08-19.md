# Релиз А. Новые справочные данные

## А1. Регион в карточке ДПО

### Цель

Пользователь вручную назначает каждому ДПО регион. Регион затем используется в печатной форме работников и может применяться как фильтр отчётов.

### Требования

- Добавить в `dpos` поле `region` типа string, длина до 255 символов, nullable.
- В карточке создания/редактирования ДПО добавить понятное поле **«Регион»**.
- Регион должен входить в историю изменений ДПО (`DpoHistory`), чтобы изменение региона не уничтожало исторический снимок реквизитов.
- В списке ДПО показать колонку «Регион».
- В стартовом Excel-импорте ДПО поддержать необязательную колонку «Регион». Старые файлы без неё должны продолжать импортироваться.
- Пустой регион не блокирует сохранение ДПО. В отчётах вместо пустого значения показывать `—`.

### Критерии приёмки

- Регион можно назначить и изменить в интерфейсе ДПО.
- После изменения в истории ДПО видны старое и новое значения.
- Регион возвращается API и доступен отчётам.
- Существующие ДПО без региона продолжают работать.

## А2. Категория номенклатуры по полу

### Причина изменения

Сейчас пол указан у строки комплекта должности (`PositionKitItem.gender`), а не у модели номенклатуры. Одна модель может встретиться в разных комплектах, поэтому выводить «мужское/женское» в остатках только по комплектам неоднозначно.

### Требования

- Добавить модели номенклатуры поле `genderCategory` со значениями:

  - `male` — мужское;
  - `female` — женское;
  - `unisex` — унисекс;
  - `unspecified` — не определено.

- Значение по умолчанию для существующих записей — `unspecified`. Не угадывать пол по названию вещи.
- В карточке номенклатуры добавить обязательный понятный выбор **«Категория по полу»** с четырьмя русскими вариантами.
- В стартовом импорте номенклатуры добавить необязательную колонку «Категория по полу».
- Сохранить `PositionKitItem.gender`: это отдельное правило применимости вещи в конкретном комплекте. Не заменять его новым полем.
- При желании сделать отдельную проверку качества данных: список моделей с `unspecified`. Она полезна, но не должна блокировать релиз.

### Критерии приёмки

- Новую модель нельзя случайно сохранить с непонятным машинным значением; UI показывает русские подписи.
- Старые модели после миграции имеют «Не определено» и не пропадают из остатков.
- Пол комплекта продолжает работать независимо от категории модели.

# Релиз Б. Остатки: удобная сортировка и фильтры

## Цель

На странице **«Склады → Остатки»** кладовщик должен быстро увидеть, на каком складе лежит конкретная модель, в каких размерах и ростах, а также относится ли модель к мужской, женской или универсальной одежде.

## Обязательный результат

Таблица содержит колонки в таком порядке:

1. Склад;
2. Категория по полу;
3. Модель;
4. Размер;
5. Рост;
6. Количество.

## Фильтры

- Склад — один или все.
- Категория по полу — все / мужское / женское / унисекс / не определено.
- Модель — строка поиска по части названия или существующий выбор модели с поиском.
- Размер — необязательный фильтр.
- Рост — необязательный фильтр.
- Кнопка **«Сбросить фильтры»**.

## Сортировка

- Клик по каждому заголовку переключает `ASC/DESC`.
- Добавить составную сортировку по умолчанию:

  `Склад → Категория по полу → Модель → Размер → Рост`.

- Размер и рост сортировать как числовые значения, где это возможно: `44, 46, 48, 50`, а не `44, 46, 50, 48` и не лексикографически `100, 44, 46`.
- Пустые размер/рост размещать после заполненных при сортировке по возрастанию.
- При одинаковом основном значении использовать стабильные дополнительные ключи, чтобы строки не «прыгали» после обновления.
- Сортировка и фильтры должны выполняться одинаково в таблице, Excel и PDF.

## Представление данных

- Сохранять одну строку на уникальное сочетание: склад + модель + размер + рост.
- Внизу показывать суммарное количество по текущей выборке.
- Отображать число найденных позиций.
- Сохранять выбранные фильтры в URL query-параметрах желательно, но это не блокирует первый релиз.

## Печатная форма остатков

- Excel и PDF используют текущие фильтры и текущую сортировку.
- Колонки печатной формы: Склад, Категория по полу, Модель, Размер, Рост, Количество.
- В форме указать дату и время формирования.
- В конце — итоговое количество.
- Не возвращать закупочную цену и иные скрытые стоимостные поля.

## Полезное дополнительное улучшение, не обязательное для первого релиза

Добавить колонку **«Ожидает довыдачи»** — сумму открытых задач на доукомплектовку для этого склада/модели/размера/роста. Тогда кладовщик сразу видит не только остаток, но и фактическую потребность. Реализовывать только отдельным небольшим коммитом после основной сортировки.

## Тесты

- Несколько складов, моделей, размеров `8`, `10`, `46`, `100` и пустой размер.
- Мужская, женская, унисекс и неопределённая модель.
- Проверка каждого фильтра и обоих направлений сортировки.
- Проверка составной сортировки по умолчанию.
- Проверка совпадения порядка строк API и экспорта.

## Критерии приёмки

# Релиз Г. Отчёт «Сменяемость работников по ДПО»

## Бизнес-цель

За выбранный период показать, сколько работников было в ДПО, сколько принято и уволено, и рассчитать понятный показатель сменяемости. Должна быть возможность анализировать результат по должности и полу.

## Формула первого релиза

Пока заказчик не утвердил другую методику, использовать следующую явно подписанную формулу:

`Средняя численность = (численность на начало + численность на конец) / 2`

`Сменяемость, % = min(принято за период, уволено за период) / средняя численность × 100`

Если средняя численность равна нулю, сменяемость равна `0`, а не `NaN`/бесконечности.

Также отдельно показывать:

- численность на начало периода;
- принято за период;
- уволено за период;
- численность на конец периода;
- среднюю численность;
- сменяемость, %;
- справочно: оборот кадров, `% = (принято + уволено) / средняя численность × 100`.

Название формулы и подсказку вывести прямо на странице, чтобы пользователь понимал расчёт. Не называть этот показатель «текучестью»: причин увольнения в системе нет, поэтому корректно вычислить текучесть пока невозможно.

## Период и принадлежность к ДПО

- Обязателен период `с/по`.
- Фильтр ДПО: один или все.
- Принадлежность работника к ДПО определять по `EmployeeDpoAssignment` на соответствующую дату, а не только по текущему `employee.dpoId`.
- Принятый учитывается по `hireDate`, уволенный — по `terminationDate`.
- Численность на начало/конец — работники, трудовые отношения которых активны на соответствующую дату и которые назначены этому ДПО на эту дату.
- Если у работника отсутствует дата приёма, он может входить в текущую численность, но не должен считаться принятым за период. В интерфейсе желательно показать предупреждение о количестве неполных карточек.

## Должность и пол

- Фильтры: должность и пол (все / мужской / женский / не указан).
- Группировка: переключатель **«По ДПО» / «По должности» / «По полу» / «ДПО + должность + пол»**.
- Сортировка по ДПО, должности, полу, численности и проценту сменяемости.
- Для первой версии использовать текущую должность работника, потому что истории должностей в системе нет. Обязательно показать примечание в отчёте: «Должность указана по текущей карточке работника».

## Таблица

Минимальные колонки:

1. ДПО;
2. Должность;
3. Пол;
4. На начало;
5. Принято;
6. Уволено;
7. На конец;
8. Средняя численность;
9. Сменяемость, %;
10. Оборот кадров, %.

В зависимости от выбранной группировки ненужные измерения можно скрывать, но Excel/PDF должны явно отражать выбранную группировку.

## Экспорт

- Excel и PDF с названием «Сменяемость работников по ДПО».
- Показывать период, фильтры и формулу.
- Проценты округлять до двух знаков только при отображении; расчёт выполнять без промежуточного округления.
- Итоговая строка должна пересчитываться из общих чисел, а не складывать проценты отдельных строк.

## Ограничение данных

Без причины увольнения нельзя рассчитывать классический коэффициент текучести по собственному желанию/нарушениям. Если заказчику понадобится именно текучесть, отдельным релизом добавить справочник причин увольнения и поле причины в карточку работника.

## Тестовые сценарии

- В ДПО на начало 10 работников, за период принято 3, уволено 2, на конец 11: средняя численность `10.5`, сменяемость `19.05%`, оборот `47.62%`.
- Нулевая средняя численность.
- Работник переведён между двумя ДПО внутри периода.
- Работник без пола, должности или даты приёма.
- Фильтры по должности и полу.
- Общий итог не является суммой процентов строк.

## Критерии приёмки

- Показатель воспроизводим вручную по формуле, указанной на экране.
- Перевод между ДПО учитывается по истории назначений.
- Фильтры и группировки одинаково работают на экране, в Excel и PDF.
- Отчёт не выдаёт «текучесть» за сменяемость без данных о причинах увольнения.

# Релиз Д. Доукомплектовка как полноценная отдельная выдача

## Текущее поведение

В системе уже есть страница задач на доукомплектовку. При нажатии «Завершить» сервер автоматически создаёт и сразу проводит отдельный документ выдачи для одной задачи. Это технически создаёт выдачу, но пользователь не видит обычный сценарий черновика, не может проверить/скорректировать состав перед проведением и не получает очевидный переход к сохранной расписке.

## Требуемое поведение

Задача на доукомплектовку должна оформляться через обычный самостоятельный документ **«Выдача»** со всеми стандартными последствиями:

- собственный номер и дата;
- работник, ДПО, склад и ответственный;
- строки номенклатуры с размером, ростом и количеством;
- проведение и складские движения;
- имущество в карточке работника;
- участие во всех штатных печатных формах и отчётах;
- возможность открыть документ из списка выдач;
- формирование сохранной расписки по этой довыдаче;
- стандартное контролируемое редактирование проведённой выдачи, если оно уже разрешено системой.

## Новый пользовательский сценарий

1. На странице задач пользователь раскрывает работника.
2. Нажимает **«Оформить довыдачу»**.
3. Система объединяет выбранные открытые позиции одного работника и одного склада в новый черновик выдачи.
4. Открывается обычный редактор выдачи с уже заполненными работником, складом и строками.
5. Пользователь проверяет дату, ответственного и количество; при необходимости уменьшает количество, но не может добавить больше открытой потребности без явного ручного добавления обычной позиции.
6. Пользователь проводит документ штатной кнопкой «Провести».
7. Только после успешного проведения связанные задачи становятся завершёнными.
8. На странице проведённого документа видна кнопка **«Сохранная расписка»**. Она формирует расписку именно по строкам этой довыдачи.

## Группировка задач

- Один документ выдачи относится только к одному работнику и одному складу.
- Если у работника открытые задачи по разным складам, создавать отдельные документы по каждому складу.
- По умолчанию выбирать все открытые задачи работника на выбранном складе.
- Разрешить снять отдельную позицию перед созданием черновика.
- Одна задача не должна одновременно попасть в два активных черновика.

## Жизненный цикл задачи

Рекомендуемые статусы:

- `open` — ожидает оформления;
- `in_progress` — создан связанный черновик выдачи;
- `completed` — связанный документ успешно проведён;
- `cancelled` — только если появится явная операция отмены с причиной; в первый релиз можно не добавлять.

Правила:

- Создание черновика переводит выбранные задачи в `in_progress` и связывает их с документом.
- Удаление связанного черновика возвращает задачи в `open`.
- Проведение документа переводит задачи в `completed` в той же транзакции, что и складское движение.
- Ошибка проведения оставляет задачи `in_progress`, документ — черновиком, остатки не меняются.
- Изменение или отмена проведённой довыдачи должно корректно обновлять связь и количество. Не оставлять задачу завершённой, если фактическая довыдача отменена.

## Количество и частичное закрытие

- Если в черновике выдано меньше, чем требовалось, завершить исходную задачу только на фактически выданную часть и оставить открытый остаток потребности.
- Предпочтительная модель данных — отдельная таблица связи/исполнения задачи с документом и количеством, например `issuance_task_fulfillments(task_id, document_id, quantity)`. Она безопаснее одного `fulfillingDocumentId`, если одна потребность закрывается несколькими документами.
- Не создавать рекурсивные дубликаты задач при проведении документа довыдачи. Остаток должен обновлять исходную потребность либо создавать строго одну новую задачу с явной связью с исходной.
- Сумма исполнений не может превышать исходное требуемое количество.

## Сохранная расписка

- Использовать существующий модуль `print-forms/preservation-receipt`, не создавать второй независимый генератор.
- Расписка формируется по конкретному проведённому документу довыдачи и включает фактически выданное количество.
- Если бизнес-форма сейчас формируется только по работнику/периоду и смешивает несколько выдач, расширить контекст параметром `issuanceDocumentId`, сохранив обратную совместимость существующих вызовов.
- После проведения показать явное успешное действие: **«Скачать сохранную расписку»** и ссылку **«Открыть выдачу»**.

## Страница задач

- Заменить действие «Завершить» на понятное **«Оформить довыдачу»**.
- Показывать статус: ожидает / черновик создан / выдано.
- Для `in_progress` показывать ссылку на черновик.
- Для `completed` показывать ссылку на проведённую выдачу и сохранную расписку.
- В строке работника показывать количество открытых позиций и общее недостающее количество.
- Сохранить фильтры открытых и завершённых; добавить «В оформлении».

## Транзакции и конкурентность

- Блокировать выбранные задачи на время создания/проведения, чтобы два кладовщика не оформили одну потребность дважды.
- Проверять остаток повторно именно при проведении.
- Связь задачи, проведение документа, движения экземпляров и смена статуса должны фиксироваться атомарно.
- При конфликте возвращать понятное сообщение пользователю, а не общий `500`.

## Тесты

- Одна задача → черновик → проведение → отдельная выдача → сохранная расписка.
- Несколько задач одного работника и склада объединяются в одну выдачу.
- Задачи одного работника по разным складам не объединяются.
- Двойной клик/два пользователя не создают два документа.
- Удаление черновика возвращает задачи в `open`.
- Недостаточный остаток при проведении не закрывает задачу.
- Частичная довыдача оставляет точный открытый остаток.
- Отмена/редактирование проведённой довыдачи не ломает остатки и статус задачи.
- Сохранная расписка содержит только фактически выданные строки этого документа.

## Критерии приёмки

- Доукомплектовка видна в общем списке выдач как отдельный документ.
- Пользователь может проверить черновик до проведения.
- После проведения правильно меняются склад и имущество работника.
- По документу доступна сохранная расписка.
- Одна потребность не может быть выдана дважды.
- Статус задачи всегда соответствует фактическому состоянию связанного документа.

# 7. Вопросы, которые нужно подтвердить у заказчика, но они не блокируют начало базовой реализации

1. Под «сменяемостью» действительно понимается `min(принято, уволено) / средняя численность × 100`? Формула выше выбрана как рабочая и должна быть явно видна пользователю.
2. Нужны ли причины увольнения и отдельный показатель текучести? Сейчас таких данных нет.
3. «Статус работника» должен вычисляться автоматически или заказчику нужен ручной справочник статусов (например, декрет, отпуск, временно не работает)? В первом релизе статус автоматический.
4. Должна ли сохранная расписка автоматически скачиваться сразу после проведения довыдачи или достаточно явной кнопки? Рекомендуется кнопка, чтобы браузер не блокировал автоматическую загрузку.
5. Нужно ли включать унисекс в мужскую и женскую выборки остатков или показывать отдельной категорией? В этом ТЗ унисекс — отдельная категория.

# 8. Финальная проверка всей серии

- Миграции применяются на чистой БД и на копии существующей БД.
- Старые ДПО и номенклатура не пропадают из интерфейса.
- Остатки, Excel и PDF совпадают.
- Печатная форма работников содержит только шесть согласованных колонок.
- Отчёт сменяемости воспроизводится вручную на контрольном наборе.
- Полный цикл довыдачи проверен через UI, а не только API-тестами.
- После успешного `pnpm release:check` обновить `HANDOFF.md`, руководство пользователя и демонстрационный сценарий.
- Коммиты отправить в текущую ветку только после зелёного полного прогона.
