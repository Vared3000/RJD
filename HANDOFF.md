## Локальное окружение — важные отличия от "стандартного" сетапа

- **Docker не установлен** на этой машине. `docker-compose.yml` написан и
  предназначен для сервера предприятия (раздел 4 ТЗ — развёртывание без
  интернета), но локальная разработка идёт напрямую против **локального
  PostgreSQL 18** (Windows-сервис `postgresql-x64-18`, уже запущен).
- БД `workwear_erp`, роль `workwear_app` / пароль `workwear_app_password` —
  создана отдельно от суперпользователя, не пересекается с базой `cleanflow`
  соседнего (чужого) проекта на этой же машине.
- `.env` в корне уже заполнен рабочими значениями (скопирован из
  `.env.example`), включая `BOOTSTRAP_ADMIN_PASSWORD=change-me-on-first-login`
  для входа как `admin`.
- **Git Bash на Windows ломает кириллицу в inline-аргументах** к нативным
  .exe (`curl -d '{"name":"Русский текст"}'`, `psql -c "... WHERE x = 'рус'"`)
  — байты манглятся при передаче argv в дочерний процесс. Для тестовых
  запросов с кириллицей писать payload в файл и передавать через
  `curl --data-binary @file.json` / `psql -f file.sql`, либо гонять кириллицу
  только через stdin (пайпы это не ломает). Сами данные в БД/приложении не
  повреждаются — проверено сквозным byte-level тестом, проблема только в
  этом одном инструменте тестирования.

## Как проверялась каждая фича (и как проверять дальше)

1. `pnpm --filter @workwear/server test` — автотесты (сейчас 7/7, файлы в
   `server/src/tests/*.test.js`). **Ходят в реальную dev-БД**, не в откатываемой
   транзакции — каждый новый тест обязан подчищать за собой через
   `t.after()`, см. `docs/architecture.md` раздел "Тесты, создающие данные".
2. Живой прогон в headless-браузере через Playwright, вручную установленный в
   scratchpad (`C:\Users\user\AppData\Local\Temp\claude\...\scratchpad\pw-check\`,
   там же `driver.mjs` — REPL-драйвер с командами `launch/nav/fill/click-text/
   click-dialog-text/select-label/wait-text/ss/console-errors/quit`). Это НЕ
   часть репозитория проекта — придётся либо переустановить в новом
   scratchpad (`npm install playwright && npx playwright install chromium`),
   либо написать драйвер заново по образцу `.claude` skill `run` →
   `examples/playwright.md`. Оправдало себя дважды: поймало реальные баги,
   которые не всплыли бы при проверке только по коду или только через curl
   (несработавшие defaultValue в формах, `FOR UPDATE` через LEFT JOIN).
3. После ручных проверок — чистить тестовые данные из dev-БД (см. примеры
   `DELETE FROM ...` в истории команд/`docs/architecture.md`), чтобы не
   путать реальные данные с мусором на следующей сессии.

## Следующая задача: Этап 8 — Выдача/возврат

Этап 7 (Работники) реализован и проверен в этой сессии — CRUD карточки
(`server/src/modules/employees/`, `client/src/pages/employees/
EmployeesPage.jsx`), стаж считается на лету. См. подробную запись выше.
Не переоткрывать её — но учитывать, что карточка работника **сознательно
неполная** относительно раздела 8 ТЗ: полей "история выдач", "история
документов" и "стоимость имущества" в ней ещё нет. Это открытый пункт,
который нужно закрыть **на этом, Этапе 8** (не откладывать дальше) —
после реализации документа "Выдача" эти три раздела карточки работника
осмысленно наполняются:
- история выдач/документов — список документов Выдачи/Возврата по
  `employeeId`, аналогично тому, как `/stock/movements` (Этап 6) показывает
  историю по складу;
- стоимость имущества — сумма `cost`/`employeeCost` выданных и ещё не
  возвращённых `Instance` по этому работнику (нужен способ связать
  `Instance` с работником — вероятно, `employeeId` на самом экземпляре,
  проставляемый документом Выдачи и очищаемый документом Возврата,
  аналогично тому, как `warehouseId` у `Instance` меняется документом
  Поступления/Перемещения).

Из раздела 11 ТЗ ("Складские документы") и раздела 9 ("Комплекты"):
документ "Выдача" должен уметь как выдавать конкретные экземпляры вручную,
так и "быстрый подбор комплекта" — система предлагает комплект по
должности работника и его размерам, проверяет наличие на складе, создаёт
документ выдачи. Комплект как сущность (какие модели нужны для какой
должности) нигде ещё не описан в БД — потребуется отдельная таблица
"комплект по должности" (или похожая), т.к. `Position` сейчас не хранит
такой связи. Документ "Выдача" по структуре должен быть похож на
"Поступление" (Этап 5): шапка + строки + необратимое проведение
(`server/src/modules/purchases/receiving/` — образец: транзакция,
`SELECT ... FOR UPDATE` без include на блокировке, `StockMovement` при
проведении), но вместо создания новых `Instance` — перевод существующих
из `status='in_stock'` в `status='issued'` (и наоборот при Возврате),
плюс простановка/сброс `employeeId`. "Возврат" может быть либо отдельным
документом (как в разделе 11 ТЗ), либо операцией внутри Выдачи — решить
при реализации, ориентируясь на естественность UI, а не строго следовать
заголовку раздела ТЗ буквально.

Права уже в каталоге: `issuance.manage` (назначено `warehouse_manager`,
`hr_manager`). Код модуля — `issuance` (см. таблицу соответствий в
`docs/architecture.md`).
