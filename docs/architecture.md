# Архитектурные соглашения

Эти правила действуют для всех последующих этапов (см. PROJECT_SPECIFICATION.md,
раздел 17) и не должны нарушаться без явного пересмотра — цель проекта прямо
требует масштабируемости без переписывания ядра.

## Backend: Controller → Service → Repository

Каждый модуль в `server/src/modules/<module>/`:

- `*.routes.js` — только маршруты + JSDoc для Swagger, вызывает контроллер.
- `*.controller.js` — HTTP-слой: парсинг запроса, вызов сервиса, формирование
  ответа через `utils/respond.js`. Никакой бизнес-логики.
- `*.service.js` — бизнес-логика и оркестрация. Не знает про `req`/`res`.
- `*.repository.js` — единственное место обращения к Sequelize-моделям.
- `*.validation.js` — zod-схемы входных данных.

Ошибки — только через `ApiError` (`utils/api-error.js`) или естественные
исключения Sequelize/zod; центральный `errorHandler` сам сопоставит их с HTTP-
статусами. Не отправлять `res.status().json()` с ошибкой напрямую из сервиса/
репозитория.

## Данные

- Первичные ключи — `UUID` (`DataTypes.UUIDV4`) везде, без исключений.
- Столбцы в БД — `snake_case` (`underscored: true` в sequelize.js), в JS-коде —
  `camelCase` через `field:` в определении модели.
- Мягкое удаление — через `archivedAt` (nullable `DATE`), без физического
  DELETE и без отдельного булева `isActive`/`status` для этой цели. Причина:
  складские документы и печатные формы должны сохранять корректные ссылки на
  архивные записи (номенклатура, работники, склады и т.д.) даже после архивации.
  Выборки для **создания новых** документов фильтруют `archivedAt: null`;
  `include` в **уже существующих** документах — без фильтра.
- Изменение остатков склада — только через складские документы (раздел 11 ТЗ),
  никогда прямым UPDATE количества.

## Права доступа

Единый каталог прав — `server/src/config/permissions.js` (коды вида
`module.action`, например `nomenclature.manage`). Роли — `RolePermission`
многие-ко-многим. При добавлении нового модуля: добавить его права в каталог,
привязать к нужным ролям, защищать роуты через
`requirePermission('module.action')`.

## Frontend: Feature-Sliced Design

Слои и правило зависимостей (выше может импортировать только из нижних слоёв):

```
app → pages → widgets → features → shared
```

- `shared/` не импортирует ничего из `features/pages/widgets` — в частности,
  состояние сессии живёт в `shared/session/session-store.js`, а не в
  `features/auth`, потому что `shared/api/http-client.js` должно иметь к нему
  доступ для авто-обновления токена по 401.
- `entities/` пока не создан — появится, когда возникнет первая настоящая
  бизнес-сущность с собственной моделью данных на фронтенде (работник,
  номенклатура и т.п.), а не раньше (без пустых слоёв "про запас").
- Токен доступа хранится только в памяти (Zustand), не в localStorage —
  устойчивость к XSS. При перезагрузке страницы сессия молча восстанавливается
  через `POST /auth/refresh` (httpOnly cookie).
- Стили — CSS Modules, колокейтед с компонентом (`Component.module.css`).
  Общие токены (цвета, отступы) — CSS-переменные в `app/styles/global.css`.

## CatalogPage: конфигурируемый список+форма для справочников

`features/catalogs/ui/CatalogPage.jsx` — общий компонент (таблица +
модальная форма на RHF+Zod + архивирование/восстановление), которым
реализованы все справочники и номенклатура (см. таблицу конфигурации в
`pages/catalogs/*` и `pages/nomenclature/*`). При добавлении новой сущности
через `CatalogPage`, а не с нуля:

- **Если в zod-схеме поля есть `.default(...)`, продублируйте его в
  `field.defaultValue`.** RHF инициализирует пустые поля пустой строкой, а не
  `undefined`, поэтому `.default()` в схеме молча не сработает и форма
  покажет ошибку валидации на пустом с виду поле. `defaultValuesFor()` в
  `CatalogPage.jsx` подставляет `field.defaultValue` только при создании
  (не при редактировании существующей записи).
- **Числовые поля регистрируются без `valueAsNumber`** (см.
  `CatalogFormField.jsx`) — иначе RHF превращает пустую строку в `NaN` ещё до
  zod, и `z.preprocess` для опциональных числовых полей (пример:
  `instance.validation.js`, поле `cost`) не успевает увидеть пустую строку.
  Строка → число приводит сама схема через `z.coerce.number()`.
- `optionValue`/`optionLabel` в конфиге `select`-поля принимают либо строку
  (имя свойства), либо функцию `(item) => ...` — используйте функцию, когда
  подпись нужно собрать из нескольких полей (пример: размер в
  `InstancesPage.jsx` — `"Обувь: 42"`).
- Если у сущности есть собственное бизнес-поле с названием "статус" (как
  `Instance.status` — этап жизненного цикла), передавайте
  `archiveColumnLabel` в `CatalogPage`, чтобы не путать его со встроенной
  колонкой архивации/восстановления.
