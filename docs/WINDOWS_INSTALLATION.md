# Установка и эксплуатация на Windows

Система устанавливается нативно, без Docker. Frontend собирается один раз и
раздаётся backend-процессом; PostgreSQL принимает подключения только на самом
сервере. Пользователи открывают один адрес в локальной сети.

## Требования

- Windows 10/11 x64 или Windows Server 2019 и новее;
- учётная запись локального администратора на время установки;
- не менее 5 ГБ свободного места;
- постоянный IPv4 сервера и подсеть рабочих мест в формате CIDR;
- две доступные UNC-папки на разных компьютерах для второй и третьей копии;
- учётная запись Windows с правом чтения и записи в обе сетевые папки;
- интернет на время первичной установки и планового обновления.

Установщик проверяет или устанавливает через `winget` Node.js 24 LTS, pnpm 11,
Git и PostgreSQL 18. Официальный установщик PostgreSQL запускается интерактивно:
пароль суперпользователя не передаётся в командной строке и журнале.

## Первичная установка

1. Скопируйте весь каталог проекта на сервер в постоянное место.
2. Запустите `Установить программу.bat`.
3. Подтвердите запрос UAC.
4. Укажите локальный IPv4 сервера, разрешённую подсеть, пароль администратора
   PostgreSQL, пароль первого администратора приложения, две сетевые папки и
   учётную запись Windows для резервного копирования.
5. Дождитесь сообщения об успешной проверке `/health` и откройте созданный ярлык.

Сценарий создаёт отдельную роль и базу приложения, безопасный `.env`, применяет
миграции и начальные данные, собирает frontend, регистрирует службу
`WorkwearERP`, ограничивает правило Windows Firewall локальной подсетью и
настраивает ежедневную резервную копию на всех трёх ПК и сразу проверяет запуск
задания под его рабочей учётной записью.

Файл `.env` создаётся через временный файл и атомарную замену. Полный доступ к
нему остаётся только у локальных администраторов и `SYSTEM`; служебная учётная
запись резервного копирования получает только чтение. Пароли и секреты не
пишутся в журналы. Повторный запуск установщика обновляет существующую
установку и не создаёт дубликаты службы, ролей, базы или задания планировщика.

## Служба и автозапуск

Node.js запускается системной службой через WinSW 2.12.0. Установщик скачивает
официальный бинарный файл и до регистрации проверяет закреплённую SHA-256 сумму.
Служба зависит от PostgreSQL, стартует автоматически без входа пользователя и
перезапускается после аварийного завершения.

## Ежедневное управление

| Файл | Назначение |
|---|---|
| `Запустить программу.bat` | Запустить службы, проверить `/health`, открыть браузер |
| `Остановить программу.bat` | Штатно остановить приложение для обслуживания |
| `Проверить состояние.bat` | Показать состояние служб, БД, HTTP и путь к журналам |
| `Создать резервную копию.bat` | Немедленно создать и проверить копии на всех трёх ПК |
| `Восстановить из копии.bat` | Выбрать `.dump`, подтвердить и восстановить базу |
| `Обновить программу.bat` | Безопасно получить и применить новый релиз |
| `Провести приёмку.bat` | Проверить сервер и сформировать отчёт приёмки |

Установщик также создаёт общие ярлыки «РЖД Спецодежда — Запуск» и
«РЖД Спецодежда — Состояние». Административные операции сами запрашивают UAC.

## Безопасное обновление

`Обновить программу.bat` сначала требует успешную резервную копию на основной
диск и оба резервных ПК, затем получает изменения только fast-forward, устанавливает
закреплённые зависимости, собирает приложение, выполняет миграции и проверяет
`/health`. Если этап не завершился, сценарий возвращает файлы на точный прежний
commit; если миграции уже начались — восстанавливает сделанную перед обновлением
копию базы. Обновление не запускается при незакоммиченных изменениях файлов.

## Диагностика

`Проверить состояние.bat` использует коды возврата:

- `0` — приложение и база работают;
- `1` — служба приложения не работает;
- `2` — PostgreSQL не работает;
- `3` — служба запущена, но `/health` не отвечает.

Журналы установки и управления находятся в `logs/windows`, журналы службы — в
`logs/service`. При обращении в поддержку приложите
последний файл из обоих каталогов, предварительно проверив его на служебные
данные организации.

## Приёмка на целевом сервере

После установки администратор должен отдельно проверить:

- доступность программы после полной перезагрузки сервера;
- вход с двух рабочих мест разрешённой подсети;
- отсутствие доступа из другой подсети и из интернета;
- создание одинакового комплекта копий на всех трёх ПК по расписанию;
- тестовое восстановление свежей копии по регламенту резервного копирования.

Автоматические доказательства и поля для ручных результатов собраны в
[протоколе приёмки](WINDOWS_ACCEPTANCE_PROTOCOL.md).
