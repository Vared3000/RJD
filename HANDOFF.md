## Текущий статус (31.07.2026, Этап 12)

Реализованы пять обязательных печатных форм: ФПУ-26, приложение 1.5,
приложение 1.7, личная карточка работника и УПД. Первые четыре доступны в
Excel и PDF, УПД — в PDF через `GET /api/v1/print-forms/:form` и экран
`/print-forms`. Excel содержит формулы, итоги, стили и область печати; PDF —
кириллицу DejaVu, повторную шапку таблицы, подписи и корректную
многостраничную нумерацию.

Источник выбирается автоматически: проведённые документы выдачи имеют
приоритет, а при их отсутствии модуль читает нормализованные строки архива
из `source_import_records`. Семантически одинаковые копии актов не
дублируют суммы. Реальная проверка по Калининградской ДПО за июль 2026 дала
60 единиц и итог 71 918,9262 руб.; все три реальные формы проверены
визуально в Excel/PDF. Реквизиты ДПО восстанавливаются на дату окончания
периода через `DpoHistory`.

Экстрактор/импортёр сохраняют нормализованные кандидаты отдельно от исходных
строк, заполняют реквизиты всех 15 ДПО, разбирают 27 архивных личных карточек
на работников, размеры, 338 строк номенклатуры, нормы, сроки использования и
даты выдачи/возврата, а также 18 строк исходного УПД. В исходных данных ошибок
разбора нет. Реальный УПД № 172 за 31.07.2026 воспроизводит двухстраничную
официальную форму; суммы 3 827 092,23 + НДС 191 354,63 =
4 018 446,86 руб. сверены с исходным PDF.

Проверки: backend 17/17 и ESLint зелёные; перед коммитом также запускается
production build клиента. Этап 12 закрыт полностью: все девять JSON-отчётов
теперь имеют Excel/PDF-экспорт через `/api/v1/reports/:report/export`, а на
каждом экране отчёта есть две кнопки скачивания. Экспорты повторно используют
существующие расчёты и текущие фильтры, содержат период, итоги и точность денег
до тысячных.

Импорт дополнительно защищён от ложных работников из подписных строк
(`Начальник ...`, `Настоящий Акт Сторон`, `Претензий ...`, `Сохранная ...`).
Повторный импорт удаляет только устаревшие `normalized_candidate` текущих
исходных файлов, архивирует уже созданный шум и сохраняет двух реальных
работников без табельного номера. На `/print-forms` работник выбирается
поиском по ФИО/табельному номеру после выбора ДПО.

Составной размер одежды завершён полностью: `Instance`/`ReceivingLine`/
`IssuanceLine` хранят основной размер и рост, автоподбор комплекта учитывает
обе оси, добавлены типы `headwear`/`belt`/`gloves`, интерфейс и тест. Старый

## Локальное окружение — важные отличия от "стандартного" сетапа

- **Docker не установлен** на этой машине. `docker-compose.yml` написан и
  предназначен для сервера предприятия (раздел 4 ТЗ — развёртывание без
  интернета), но локальная разработка идёт напрямую против локального
  PostgreSQL 18 (Windows-сервис `postgresql-x64-18`, уже запущен).
- БД `workwear_erp`, роль `workwear_app` / пароль `workwear_app_password` —
  создана отдельно от суперпользователя, не пересекается с базой `cleanflow`
  соседнего (чужого) проекта на этой же машине.
- `.env` в корне уже заполнен рабочими значениями (скопирован из
  `.env.example`), включая `BOOTSTRAP_ADMIN_PASSWORD=change-me-on-first-login`
  для входа как `admin`.
- Git Bash на Windows ломает кириллицу в inline-аргументах к нативным
  .exe (`curl -d '{"name":"Русский текст"}'`, `psql -c "... WHERE x = 'рус'"`)
  — байты манглятся при передаче argv в дочерний процесс. Для тестовых
  запросов с кириллицей писать payload в файл и передавать через
  `curl --data-binary @file.json` / `psql -f file.sql`, либо гонять кириллицу
  только через stdin (пайпы это не ломает), либо просто использовать
  латинские тестовые имена (`pwwhdocs<timestamp>` и т.п.) — так делали
  Playwright-проверки в нескольких сессиях подряд. Сами данные в БД/
  приложении не повреждаются — проблема только в этом одном инструменте
  тестирования.
- Инструменты Read/Write/Edit иногда не видят файл, который только что сами
  создали в этой же кириллической папке (`2-этаж Ржд`) — ошибка "File does
  not exist" сразу после успешного создания, притом что повторный вызов того
  же инструмента с тем же путём затем срабатывает. Природа не установлена
  окончательно (подозрение на рассинхронизацию с OneDrive, который часто
  делает Known Folder Move для `Desktop` на Windows, либо на путаницу
  Unicode-эквивалентных форм написания кириллицы при повторном наборе пути
  моделью) — не является багом кода проекта. Что помогает: (1) для новых
  файлов использовать `cat > relative/path <<'EOF' ... EOF` через Bash с
  относительным путём (без кириллицы вообще, если `cd` в корень проекта уже
  выполнен) — надёжнее, чем Write/Edit с абсолютным путём; (2) для правки
  существующих файлов — `perl -0pi -e` или `sed` через Bash вместо Edit;
  (3) если Read/Write/Edit всё же нужны — просто повторить вызов, обычно
  срабатывает со второго раза; (4) после Bash-правок всегда проверять
  `cat`/`grep` результат — не доверять только сообщению об успехе.

### Запуск для проверки в этой сессии

```bash
pnpm install          # если node_modules ещё нет
pnpm db:migrate
pnpm db:seed          # создаёт роли/права/админа (admin / change-me-on-first-login)
pnpm dev              # backend :4000 (Swagger: /api-docs), frontend :5173
```

Оба dev-сервера обычно уже запущены в фоне с прошлой сессии (`node --watch`
у backend подхватывает изменения файлов сам). Проверить: `curl localhost:4000/health`
и `curl -o /dev/null -w '%{http_code}' localhost:5173`. Если не отвечают —
поднять заново командой выше.

## Как проверялась каждая фича (и как проверять дальше)

1. `pnpm --filter @workwear/server test` — автотесты (сейчас 14/14, файлы в
   `server/src/tests/*.test.js`). Ходят в реальную dev-БД, не в откатываемой
   транзакции — каждый новый тест обязан подчищать за собой через
   `t.after()`, см. `docs/architecture.md` раздел "Тесты, создающие данные".
2. Живой прогон в headless-браузере через Playwright, вручную установленный в
   scratchpad (`C:\Users\user\AppData\Local\Temp\claude\...\scratchpad\pw-check\`).
   Это не часть репозитория проекта — придётся переустановить в новом
   scratchpad (`npm install playwright && npx playwright install chromium` —
   в последних сессиях занимало секунды, видимо кэш браузера уже на машине).
   Простой прямой скрипт (goto → fill → click → screenshot) под конкретный
   сценарий, а не универсальный REPL-драйвер. Селекторы: кнопки —
   `getByRole('button', { name, exact: true })` (`getByText` ловит и текст
   заголовка модалки — strict mode violation), поля `EntityFormModal`/
   `CatalogFormField` — `#<fieldName>` (id совпадает с `name`, в т.ч. у
   `Select` через `Controller`). Контролируемые чекбоксы без optimistic
   update — `.click()` + `waitForTimeout`, не `.check()` (см. Этап 10).
   Оправдало себя во всех сессиях подряд, где применялось.
3. После ручных проверок — чистить тестовые данные из dev-БД (порядок с
   учётом FK — см. `docs/architecture.md` "Тесты, создающие данные" и
   `t.after()` в тестовых файлах), чтобы не путать реальные данные с
   мусором на следующей сессии.
4. `pnpm lint` (корневой ESLint) и `pnpm --filter @workwear/client build`
   (`vite build`) — быстрая проверка компиляции клиента без запуска dev-сервера.

## Этап 12 — печатные формы (завершён)

Раздел 13 ТЗ, код модуля `print_forms` (см. таблицу соответствий в
`docs/architecture.md`), право `print_forms.use` уже в каталоге прав.

Готово: PDF/Excel для ФПУ-26, приложения 1.5, приложения 1.7 и личной
карточки работника, двухстраничный PDF УПД со статусом 1 и Excel/PDF для
всех девяти отчётов (раздел 13 ТЗ).

Референс уже на машине — папка `РЖД 2й этаж/` в корне проекта (вне git, см.
`.gitignore`) содержит реальные примеры всех этих форм за разные периоды и
филиалы (ДПО). Прежде чем проектировать генерацию — открыть и разобрать
структуру:

- `АКТ ФПУ-26 <период> <ДПО>.xlsx` — акт выполненных работ (форма ФПУ-26),
  шапка содержит реквизиты заказчика/ДПО (из новой таблицы `dpos` — уже есть
  все нужные поля: `fullName`, `okpo`, `businessUnitCode`, `directorFullName`,
  `directorBasis`, `contractNumber`/`contractDate`), таблица позиций —
  номенклатура/количество/цена/НДС.
- `Приложение 1.5 <период> <ДПО>.xlsx` — по должностям, с колонкой "Кол-во
  дней обеспечения форменной одежды в месяц" — это ровно `coverage.service.js`
  из Этапа 11, уже реализован и протестирован.
- `Приложение 1.7 <период> <ДПО>.xlsx` — по работникам, с ФИО/табельным
  номером/инвентарными номерами экземпляров.
- `Личная карточка <категория> муж.,жен..xls` — реализована как
  `personal-card`: данные берутся из проведённых выдач/возвратов, а при их
  отсутствии — из нормализованной архивной карточки; срок использования
  хранится в `PositionKitItem.serviceLifeYears`.
- `УПД (статус 1) № ... .pdf` — реализован как `upd`: 18 строк, реквизиты
  продавца/покупателя, платёжный документ, артикулы, цены, НДС, итоги и
  подписные блоки берутся из нормализованных данных исходного PDF.

Первые наблюдения (не считать данностью, проверить при реализации):

- Excel-генерация — понадобится библиотека (exceljs рекомендуется для
  формул/стилей, xlsx/SheetJS проще для голых данных) — ни одна ещё не
  установлена в проекте (проверено на конец Этапа 11).
- PDF — либо рендер HTML в PDF (puppeteer, может быть тяжеловат), либо
  прямая PDF-библиотека (pdfkit/pdf-lib).
- Реквизиты ДПО (директор/доверенность/доп.соглашение) должны браться из
  `Dpo` на дату документа, не текущие — здесь и пригодится история
  изменений ДПО из Этапа 11 (`GET /dpo/:id/history`): нужно решить, брать ли
  срез "состояние на дату Х" (потребует реализовать point-in-time
  реконструкцию поверх истории) или просто предупреждать пользователя, если
  генерирует акт за прошлый период с изменившимися с тех пор реквизитами —
  не решать самостоятельно, уточнить у пользователя объём (полная
  историческая точность vs текущие реквизиты).
- Не путать этот модуль с уже существующими карточками
  (`EmployeeCardPage.jsx`) — печатные формы это отдельный рендер/экспорт, не
  замена текущих экранных представлений.

## Где искать паттерны и грабли

`docs/architecture.md` — обязателен к прочтению перед новым модулем:
Controller/Service/Repository, конвенции БД (UUID, snake_case, soft-delete
через `archivedAt`), `CatalogPage`/`EntityFormModal` и их грабли
(`field.defaultValue`, `valueAsNumber`), паттерн документов
(шапка+строки+проведение, блокировка транзакции, `StockMovement`), порядок
очистки тестовых данных.

`server/src/modules/purchases/receiving/` — самый полный пример
draft/posted документа: routes → controller → service (транзакция
проведения) → repository, плюс zod-валидация с `preprocess` для
опциональных UUID/чисел. `server/src/modules/transfers/` — ещё один
draft/posted пример (движение на оба склада).

`server/src/modules/service-documents/` — пример двухфазного документа
(draft/sent/completed) и того, когда оправдано выносить общую фабрику для
двух похожих документов (Стирка/Ремонт), а не дублировать модуль целиком.

`server/src/modules/inventory/` — пример документа, который сознательно НЕ
меняет остатки склада (сверка, а не складская операция) — если понадобится
что-то подобное (например, черновой отчёт с последующим утверждением),
можно ориентироваться на этот паттерн (снимок при создании + подтверждение
построчно + завершение без побочных эффектов).

`server/src/modules/dpo/` — пример модуля с историей изменений (снимок
старых значений изменившихся полей + diff между соседними записями в
сервисе, не во фронтенде) и с поиском (ILIKE через `Op.or` в репозитории).
`server/src/modules/reports/` — пример read-only агрегирующего модуля без
собственных моделей (routes→controller→service→repository, переиспользует
существующие сервисы типа `stock.service.js`, а не дублирует их логику);
`coverage.service.js` там же — единственное место, где реконструируется
история владения экземплярами из `StockMovement`+шапок документов, раз
отдельной таблицы истории статусов в проекте нет.

Не трогать `C:\Users\user\Documents\Попытка в Агбис` — отдельный личный
проект другого стейкхолдера (химчистка CleanFlow ERP), просто использовался
как ориентир по стеку в начале работы. Он вне скоупа этого проекта.
