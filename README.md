# ERP «Учёт спецодежды»

Корпоративная ERP-система учёта аренды спецодежды: закупка → оприходование →
склад → выдача → эксплуатация → возврат → стирка → ремонт → повторная выдача →
списание. Полное техническое задание — [PROJECT_SPECIFICATION.md](PROJECT_SPECIFICATION.md).

## Текущий план доработки

Рабочий порядок релизов и критерии готовности находятся в
[docs/IMPROVEMENT_PLAN.md](docs/IMPROVEMENT_PLAN.md). Первый релиз от 08.08.2026
завершил комплекты по полу и сезону: одна должность и модель могут иметь
отдельные мужские, женские, летние и зимние варианты, а предпросмотр и
автозаполнение выдачи выбирают один наиболее точный вариант без дублей.

Инструкция для пользователей: [docs/USER_GUIDE.md](docs/USER_GUIDE.md).

Практический сценарий одного работника от создания до печатных форм:
[EMPLOYEE_FULL_CYCLE_SCENARIO.md](EMPLOYEE_FULL_CYCLE_SCENARIO.md).

Целевая эксплуатация — внутри одной локальной сети предприятия, без публичного
интернет-доступа.

## Стек

- **Backend**: Node.js + Express 5, Sequelize 6 (PostgreSQL), JWT, Swagger/OpenAPI
- **Frontend**: React 19 (Feature-Sliced Design), Vite, React Query, Zustand, React Hook Form + Zod
- **Инфраструктура**: Docker Compose, pnpm workspaces

## Быстрый старт (локальная разработка)

Предполагается локально установленный PostgreSQL (либо Docker — см. ниже).

```bash
cp .env.example .env      # заполнить реальными значениями
pnpm install
pnpm db:migrate
pnpm db:seed               # создаёт роли, права и администратора
pnpm dev                   # backend :4000, frontend :5173
```

Вход: логин/пароль из `BOOTSTRAP_ADMIN_LOGIN` / `BOOTSTRAP_ADMIN_PASSWORD` в `.env`.

Swagger UI: http://localhost:4000/api-docs

## Запуск через Docker Compose (для сервера предприятия)

```bash
cp .env.example .env      # заменить все пароли и секреты
docker compose up -d --build
```

Миграции и начальные роли применяются автоматически при старте backend.
Frontend доступен на порту 80, backend — на 4000. Полная инструкция:
[docs/operations.md](docs/operations.md).

## Резервное копирование БД

```bash
./scripts/backup.sh [каталог]     # pg_dump -> backups/*.dump
./scripts/restore.sh файл.dump    # восстановление (перезаписывает БД!)
```

Для показа заказчику используйте готовый
[демонстрационный сценарий](docs/demo-scenario.md).

## Импорт реальных актов РЖД

Импорт двухслойный и идемпотентный:

- каждая непустая строка `.xlsx`/`.xls`, каждая страница PDF и метаданные
  каждого файла сохраняются в `source_import_records`;
- рядом с исходными строками сохраняются отдельные нормализованные записи,
  поэтому архивные печатные формы читаются без повторного доступа к файлам;
- распознанные ДПО, ФИО, телефоны, табельные номера, должности, все варианты
  размеров, номенклатура, комплекты и цены нормализуются в рабочие таблицы;
- реквизиты всех 15 ДПО (полное наименование, адрес, ОКПО, БЕ, руководитель,
  доверенность, договор и дополнительное соглашение) берутся из шапок актов;
- `employee_measurements` сохраняет все встреченные размеры работника, даже
  если в основной карточке выбран только один текущий размер каждого типа;
- цены хранятся с точностью до четырёх знаков в `nomenclature_prices` и доступны
  по `GET /nomenclature-models/:id/prices`.

Исходная папка и промежуточный JSON содержат персональные данные и исключены из
Git (`/РЖД 2й этаж/`, `/server/tmp/`, `/tmp/`). Порядок запуска:

```powershell
python -m pip install -r scripts/requirements-import.txt
python scripts/extract-rzd-reference-data.py "РЖД 2й этаж" "server/tmp/rzd-reference-import.json"
pnpm db:migrate
pnpm --filter @workwear/server import:rzd -- .\tmp\rzd-reference-import.json
```

Повторный запуск обновляет записи по стабильному ключу источника и не создаёт
дубликаты.

## Роли и права (Этап 2)

Права хранятся как строки вида `модуль.действие` в
[server/src/config/permissions.js](server/src/config/permissions.js) — единый
каталог, который дополняется по мере реализации новых модулей. Предустановленные
роли: `admin`, `warehouse_manager`, `hr_manager`, `accountant`, `viewer`.

Авторизация — JWT: короткоживущий access-токен возвращается в теле ответа и
хранится на фронтенде только в памяти (Zustand), refresh-токен — в httpOnly
cookie с ротацией при каждом обновлении и отзывом при выходе.

## Справочники (Этап 3)

Организации, Подразделения, Должности, Склады, Поставщики, Размеры — все
шесть реализованы на общей фабрике CRUD с мягким удалением
([server/src/modules/catalogs/reference-crud.factory.js](server/src/modules/catalogs/reference-crud.factory.js))
и общей странице на фронтенде
([client/src/features/catalogs/ui/CatalogPage.jsx](client/src/features/catalogs/ui/CatalogPage.jsx)),
конфигурируемой per-сущность (колонки, поля формы, zod-схема). Подразделения
и Склады привязаны к Организации через `organizationId` с проверкой
существования при создании/правке.

## Номенклатура (Этап 4)

Иерархия Модель → Размер → Экземпляр (раздел 7 ТЗ). Модели номенклатуры —
обычный справочник (та же `CatalogPage`). Экземпляр — физическая единица
спецодежды: инвентарный номер и штрихкод генерируются автоматически
(последовательность `instance_inventory_number_seq`, формат `СО-000001`),
но могут быть заданы вручную (для переноса данных из бумажного учёта).
Статус (`in_stock/issued/laundry/repair/write_off`) отражает жизненный цикл
из раздела 1 ТЗ, состояние (`new/good/worn/damaged`) — физический износ,
независимая характеристика. Партии (`batches`) заведены на уровне БД (на них
уже ссылается экземпляр), но собственного CRUD пока нет — партия будет
создаваться документом "Поступление" на Этапе 5.

## Закупки и оприходование (Этап 5)

Документ "Поступление" (`server/src/modules/purchases/receiving/`): шапка
(поставщик, склад, дата, договор, накладная, ответственный — автоматически
текущий пользователь) + строки (модель, размер, количество, закупочная цена,
стоимость для работника, НДС). Пока черновик — шапка и строки редактируемы.

**Проведение** — необратимая операция в одной БД-транзакции с блокировкой
шапки документа (`SELECT ... FOR UPDATE`, без включения строк в тот же запрос
— Postgres не разрешает блокировку через LEFT JOIN, который иначе возник бы у
документа без строк): создаёт партию (`Batch`, код = номер документа),
экземпляры (по одному на единицу количества каждой строки, с автономером
`СО-NNNNNN`) и движения склада (`StockMovement`, `documentType: 'receiving'`,
`fromWarehouseId: null`). После проведения документ и его строки недоступны
для изменения.

`StockMovement` — общая инфраструктура движений склада для всех будущих
документов (Выдача, Возврат, Перемещение, Списание и т.д.), которую использует
уже этот, первый документ; `document_id` в ней намеренно без FK (тип документа
определяет, в какой таблице искать) — просмотр истории движений и агрегация
остатков будет отдельным разделом на Этапе 6.

Фронтенд — не `CatalogPage` (документы устроены иначе: шапка + строки +
необратимое проведение), а отдельные `ReceivingListPage`/`ReceivingEditorPage`,
переиспользующие вынесенный из `CatalogPage` компонент `EntityFormModal`
(форма-в-модалке на конфиге полей) — для шапки, для строки и для самого
справочника это одна и та же форма-обёртка.

## Склады: остатки и движения (Этап 6)

Остатки не хранятся отдельной таблицей — источник истины `Instance`
(`status='in_stock' AND archivedAt IS NULL`). Эндпоинт `GET /stock/balances`
(`server/src/modules/warehouses/stock/`) агрегирует экземпляры по
складу/модели/размеру (количество, суммарная стоимость) без Sequelize
`include` в самом запросе группировки — подписи склада/модели/размера
довешиваются отдельными запросами и мержатся в сервисе, чтобы не собирать
вручную полный список колонок для `GROUP BY` присоединённых таблиц.
`GET /stock/movements` — история из `StockMovement` (уже писалась
документом "Поступление" на Этапе 5), с фильтром по складу через `Op.or`
на `fromWarehouseId`/`toWarehouseId`.

Оба эндпоинта read-only (право `warehouse.view`, без `manage` — остатки
меняются только складскими документами, раздел 11 ТЗ). Фронтенд — два
отдельных отчёта (`StockBalancesPage`/`StockMovementsPage`), не
`CatalogPage` (агрегированные/исторические данные без CRUD).

## Работники (Этап 7)

CRUD карточки работника (`server/src/modules/employees/`) поверх той же
`reference-crud.factory.js`, что и справочники Этапа 3: организация
(обязательно), подразделение/должность (опционально, с проверкой
принадлежности подразделения указанной организации), три размера
(одежда/рост/обувь — каждый проверяется на совпадение `type` с полем).
`terminationDate` (дата увольнения) — бизнес-факт, отдельный от `archivedAt`
(мягкое удаление самой записи), по аналогии со `status`/`archivedAt` у
`Instance`. Стаж считается на лету на фронтенде
(`client/src/features/employees/model/format-tenure.js`), не хранится в БД.

История выдач/документов и стоимость имущества (раздел 8 ТЗ) в карточке
реализованы в Этапе 8, см. ниже.

## Выдача/возврат (Этап 8)

Документы "Выдача" (`server/src/modules/issuance/documents/`) и "Возврат"
(`.../returns/`) — шапка + строки + необратимое проведение, по образцу
"Поступления" (Этап 5). Выдача при проведении подбирает доступные экземпляры
FIFO под каждую строку (`FOR UPDATE SKIP LOCKED`) и переводит их в
`status='issued'` с привязкой `Instance.employeeId`; Возврат работает с уже
конкретным `instanceId` в строке и возвращает экземпляр в `in_stock` на
склад документа. "Быстрый подбор комплекта" (раздел 9 ТЗ) —
`issuanceService.applyKit`: по должности работника берёт позиции комплекта
(`server/src/modules/kits/`, таблица `position_kit_items`) и подставляет
размер работника по типу размера каждой модели.

Карточка работника (`client/src/pages/employees/EmployeeCardPage.jsx`,
маршрут `/employees/:id`) показывает стоимость выданного и ещё не
возвращённого имущества (`GET /employees/:id/property` — сумма `cost`/
`employeeCost` инстансов со `status='issued'`) и объединённую историю
документов Выдачи/Возврата по этому работнику (оба списочных эндпоинта
получили опциональный фильтр `?employeeId=`).

## Стирка/Ремонт (Этап 9)

Документы "Стирка" и "Ремонт" (`server/src/modules/laundry/`,
`.../repair/`) — структурно один и тот же документ (шапка + строки,
конкретный `instanceId` в строке, как у "Возврата"), поэтому реализованы
через общую фабрику `server/src/modules/service-documents/
service-document.factory.js`, а не продублированы: в отличие от
Поступления/Выдачи/Возврата (у каждого своя бизнес-логика проведения), тут
бизнес-правило дословно одинаковое — отличаются только целевой статус
экземпляра (`laundry`/`repair`), номер документа и то, что у Ремонта строка
дополнительно несёт стоимость ремонта (`lineExtraCompleteFields: ['cost']`).

В отличие от `draft`/`posted` у остальных складских документов, здесь два
необратимых перехода: `send` (черновик → отправлен) снимает экземпляры с
остатков — переводит `in_stock` → `laundry`/`repair` и пишет движение
склада; `complete` (отправлен → завершён) одним вызовом сразу по всем
позициям документа возвращает экземпляры в `in_stock` с итоговым
состоянием (и стоимостью ремонта, если применимо) и пишет второе движение.
Частичное завершение не предусмотрено — это осознанно долгий процесс с
одной датой завершения, а не построчное редактирование.

"Возврат" (Этап 8) получил поле `routeTo` на строке (`in_stock` по
умолчанию, либо `laundry`/`repair`) — работник может сдать вещь сразу на
стирку/в ремонт, минуя промежуточное оприходование на склад.

## Складские документы: Перемещение/Инвентаризация/Списание (Этап 10)

"Перемещение" (`server/src/modules/transfers/`) и "Списание"
(`.../writeoff/`) — draft/posted в одну транзакцию, как Поступление/Выдача/
Возврат (не через `service-documents` — у каждого своя бизнес-логика
проведения, как и у остальных draft/posted документов, см.
`docs/architecture.md`). Перемещение — единственный документ, где у
`StockMovement` заполнены оба поля `fromWarehouseId`/`toWarehouseId`
(у остальных всегда одно из двух `null`); проведение переводит
`Instance.warehouseId` на склад-получатель. Списание переводит экземпляр в
`status='write_off'` окончательно, строка обязательно несёт `reason`
(причину).

"Инвентаризация" (`server/src/modules/inventory/`) намеренно НЕ похожа на
остальные складские документы: это сверка фактического наличия с учётными
данными, а не операция, меняющая остатки. При создании документ сразу
снимает снимок остатков склада (все `status='in_stock'` экземпляры на этот
момент становятся строками с `confirmed=false`); физический пересчёт
сводится к простановке `confirmed=true` по каждой найденной позиции
(`PATCH .../lines/:lineId`). Завершение (`draft` → `completed`,
`POST .../complete`) необратимо, но **не создаёт движений склада и не
меняет `Instance.status`** — расхождения (неподтверждённые позиции)
остаются видны в завершённом документе, решение по ним (например,
списание) принимается отдельным документом "Списание". `GET`/`POST`/
`PATCH` возвращают `meta.summary = { total, confirmed, missing }`.

## Печатные формы (Этап 12, первая очередь)

Экран `/print-forms` и API `GET /api/v1/print-forms/:form` формируют:

- `fpu-26` — акт ФПУ-26 с количеством, ценой и НДС;
- `appendix-1-5` — обеспечение по должностям и дням;
- `appendix-1-7` — строки по работникам, табельным и инвентарным номерам;
- `personal-card` — личная карточка с размерами, нормами, нормативными
  сроками и историей выдачи/возврата;
- `upd` — двухстраничный УПД со статусом 1, реквизитами сторон, артикулами,
  ценами и НДС по официальной форме (только PDF).

Для периодических форм обязательны `dpoId`, `from`, `to`; для личной карточки
— `employeeId`; формат задаётся как `format=xlsx|pdf`. Excel содержит
расчётные формулы и итоги, PDF повторяет исходную разметку. Для оперативных
периодов источник — проведённые выдачи. Если их нет, модуль использует
нормализованные строки импортированных актов, личных карточек и УПД,
семантически удаляя копии одинаковых строк из разных файлов. Реквизиты ДПО
восстанавливаются на дату окончания периода из `DpoHistory`. Для УПД
поддерживается только `format=pdf`.

Выбор работника на экране становится доступен после выбора ДПО и поддерживает
поиск по ФИО или табельному номеру. Повторный импорт синхронизирует производные
нормализованные записи с исходниками и скрывает распознанные ранее служебные
заголовки, не затрагивая реальных работников без табельного номера.

Все девять экранов раздела «Отчётность» выгружают текущий набор данных и
фильтров через `GET /api/v1/reports/:report/export?format=xlsx|pdf`. Excel
содержит заголовок, период, фильтр, закреплённую шапку, автофильтр и итоги;
PDF повторяет таблицу на A4, переносит длинные отчёты на следующие страницы
и нумерует их. Денежные значения выводятся с точностью до тысячных.
