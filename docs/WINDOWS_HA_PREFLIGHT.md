# Релиз С: безопасная подготовка автоматического HA

Релиз С в репозитории — **выключенный по умолчанию лабораторный контур**, а не готовый
production-кластер. Он не создаёт Linux VM, DCS/Patroni, второй proxy/VIP и DNS автоматически.
Обычный Windows-установщик релизов П–Р для включения HA не подходит: у него локальная Windows-БД,
recovery sentinel и другой порядок запуска.

## Что уже контролирует код

- ровно три разных Patroni-хоста и один постоянный URL;
- совпадение локальных `name` и `scope` Patroni;
- локальный `/primary`, большинство из двух одинаковых cluster view и фактический
  `NOT pg_is_in_recovery()` перед каждой изменяющей операцией;
- fail-closed: replica, потеря роли, quorum или несовпадение БД дают HTTP 503;
- `synchronous_mode=quorum`, `synchronous_node_count=1` и `synchronous_mode_strict=true`
  в read-only preflight;
- безопасные GET/HEAD автоматически переподключаются не более двух минут; изменяющие запросы
  не повторяются автоматически;
- прежние бессрочные backup-задачи М–О не удаляются и не заменяются репликацией.

## Что обязательно сделать на инфраструктуре

1. На трёх разных физических ПК поднять по отдельной Linux VM с PostgreSQL, Patroni и DCS 3/3.
2. Настроить synchronous quorum + strict и `pg_rewind`/reinitialize для вернувшегося старого primary.
3. Поставить минимум два экземпляра reverse proxy и один стабильный DNS/VIP. Один proxy на одном
   ПК остаётся единой точкой отказа.
4. Разворачивать один и тот же проверенный artifact и одинаковые `JWT_*_SECRET`, `CLIENT_ORIGIN`
   на трёх app-узлах. Миграции выполнять один раз отдельным release-job, не при параллельном старте.
5. Только после этого заполнить переменные `WORKWEAR_HA_*`, включить
   `VITE_HA_RECONNECT=true`, пересобрать frontend и запустить `deploy\ha\preflight.ps1`.

Preflight печатает JSON. Параметр `-EvidencePath` создаёт новый файл и отказывается
перезаписывать существующий. Даже успешный результат имеет статус
`automatic-checks-passed-physical-pending`.

## Почему изменяющие запросы не повторяются

Потерянный HTTP-ответ не доказывает, записала ли база документ. Общий response-cache оставляет
окно между commit бизнес-транзакции и записью ответа, поэтому может создать дубликат. До внедрения
транзакционного idempotency ledger по каждой бизнес-операции интерфейс лишь сообщает о восстановлении
связи, но не повторяет POST/PUT/PATCH/DELETE.

## Физическая приёмка

Production-статус допустим только после протокола на реальных трёх ПК: выключить текущий primary,
доказать автоматическую работу через тот же URL на двух рабочих местах, проверить документы/остатки,
вернуть старый ПК только как replica, повторить при потере каждого узла и убедиться в отсутствии
дублей. До этого `WORKWEAR_HA_MODE=disabled` — обязательное состояние рабочей установки.
