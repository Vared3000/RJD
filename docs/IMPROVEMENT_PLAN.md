# План доработки ERP «Учёт спецодежды»

Дата создания: 2026-08-08
Назначение: единый рабочий план для продолжения разработки в разных сессиях и разными моделями.
Целевая эксплуатация: сервер внутри одной локальной сети предприятия, без публичного интернет-доступа.

## Как пользоваться планом

- Перед началом любой задачи прочитать `CLAUDE.md`, `HANDOFF.md` и
  `docs/architecture.md`.
- Проверить `git status` и не перезаписывать чужие незакоммиченные изменения.
- Выполнять только одну задачу плана за раз.
- Не смешивать независимые задачи в одном коммите.
- Перед миграциями проверить состояние dev-БД и сделать резервную копию, если
  изменение затрагивает существующие данные.
- Уже применённые или опубликованные миграции не редактировать. Создавать
  следующую миграцию, кроме ещё не опубликованной активной миграции текущей
  задачи.
- Бизнес-операцию, изменение экземпляра, движения и запись истории выполнять
  в одной транзакции.
- После завершения задачи обновить этот файл, `README.md` и `HANDOFF.md`.

Обязательные проверки после каждой задачи:

```powershell
pnpm.cmd lint
pnpm.cmd format:check
pnpm.cmd --filter @workwear/server test
pnpm.cmd --filter @workwear/client build
```

Если тестовая инфраструктура ещё не изолирована от dev-БД, перед запуском
backend-тестов проверить правила очистки из `docs/architecture.md`.

## Задача 4. Защитить документы от одновременной правки

Статус: **Готово** (2026-08-08).

### Цель

Проведённый документ всегда соответствует созданным движениям и изменениям
экземпляров.

### Охват

- поступление;
- выдача;
- возврат;
- перемещение;
- списание;
- инвентаризация;
- стирка;
- ремонт.

### Работы

- [x] Добавление, изменение и удаление строки выполнять в транзакции.
- [x] Блокировать шапку документа через `SELECT ... FOR UPDATE`.
- [x] После блокировки повторно проверять статус.
- [x] Не позволять изменять строки после начала проведения.
- [x] Рассмотреть поле `version` для optimistic locking.
- [x] Возвращать `409 Conflict` при конфликте конкурентных изменений.

### Тесты

Параллельно отправлять проведение и изменение строки. Допустим только один
непротиворечивый результат; проведённый документ должен совпадать с движениями.

### Результат четвёртого релиза

- Поступление, выдача, возврат, перемещение, списание, инвентаризация, стирка и
  ремонт используют одну блокировку шапки для правок и смены статуса.
- Правка шапки, добавление, изменение, удаление строки и автозаполнение
  комплекта выполняются в транзакции после `SELECT ... FOR UPDATE`.
- После ожидания блокировки статус читается повторно; проведённый, отправленный
  или завершённый документ возвращает `409 Conflict`.
- Проведение читает строки в той же транзакции после блокировки шапки, поэтому
  движения и изменения экземпляров соответствуют зафиксированному документу.
- Для инвентаризации создание шапки и снимка строк дополнительно объединено в
  одну транзакцию.
- Поле `version` не добавлялось: пессимистическая блокировка покрывает все
  серверные мутации документов и не требует изменения клиентского контракта.
- Конкурентный тест «проведение против правки строки» подтверждает: проведение
  создаёт 3 экземпляра и 3 движения, запоздавшая правка получает `409`.
- Полный изолированный прогон: 18/18 тестов.

### Результат

- Миграция `0059-create-user-admin-events.js`; модель `UserAdminEvent`
  (`server/src/database/models/`) — журнал действий с явным `eventType`
  (`create`/`role_change`/`block`/`unblock`/`password_reset`/
  `sessions_revoked`), а не общий diff по полям, как у `dpo_history`: у
  разных админ-действий разная бизнес-логика, явный тип читается однозначно.
- Модуль `server/src/modules/admin/` (право `admin.manage`, уже было в
  каталоге прав): `admin.repository.js` никогда не выбирает `passwordHash`
  (`attributes: { exclude: ['passwordHash'] }` на уровне запроса, не только
  сериализацией в контроллере). Блокировка строки пользователя — без
  `include` роли/прав (тот же принцип, что и у складских документов:
  `FOR UPDATE` через JOIN на M:N недопустим в Postgres), роль с правами
  читается отдельным запросом в той же транзакции.
- "Последний активный администратор" — не роль с кодом `admin` буквально, а
  любая роль, дающая право `admin.manage` (на случай кастомных ролей в
  будущем): перед блокировкой или сменой роли, которая убрала бы этот статус
  у пользователя, считаются остальные активные обладатели `admin.manage`;
  если ноль — `400`.
- Требования к паролю (не короче 8 символов, буквы и цифры) — общая
  zod-схема `passwordPolicy`, применяется и при создании, и при сбросе
  пароля; продублирована на фронтенде для мгновенной обратной связи в форме.
- Блокировка отзывает все refresh-токены пользователя в той же транзакции
  (`authRepository.revokeAllUserRefreshTokens`, дополнен опциональным
  параметром `transaction` — до этой задачи вызывался только из
  `auth.service.js` без транзакции).
- Frontend: `client/src/features/admin/`, `client/src/pages/admin/
  AdminUsersPage.jsx` — не через `CatalogPage` (нужны нестандартные
  построчные действия: блокировка/сброс пароля/завершение сессий, которых
  нет у общего справочника). Роли для select подгружаются переиспользованием
  `createCatalogHooks('admin/roles')` — существующая фабрика справочников
  универсальна к любому REST-пути, не только `/api/v1/<resource>` от корня.
  `CatalogFormField.jsx` получил тип поля `password` (раньше не был нужен ни
  одной форме справочника).
- Тест `server/src/tests/admin.test.js` — включая правило "последний
  администратор": проверка отклонения выполняется ДО создания тестовых
  администраторов, пока bootstrap — единственный активный обладатель

### Результат

- Миграции `0057-create-stock-adjustments.js` /
  `0058-create-stock-adjustment-lines.js`; модели `StockAdjustment` /
  `StockAdjustmentLine` (`server/src/database/models/`), право
  `adjustments.manage` (добавлено кладовщику).
- Модуль `server/src/modules/adjustments/` по паттерну шапка+строки+проведение
  (см. `docs/architecture.md`): `draft/posted`, блокировка шапки
  `SELECT ... FOR UPDATE` на любой мутации черновика и на проведении — тот же
  подход, что и у остальных складских документов.
- Тип строки (`adjustmentType`: `surplus`/`shortage`/`relocate`/`condition`)
  — дискриминированный union в zod (`adjustment.validation.js`), тип строки
  нельзя изменить после создания (только удалить и добавить заново). Поле
  `reason` (основание) обязательно для всех 4 типов — это и есть требование
  "дефицит не превращается в списание без основания", применённое единообразно
  ко всем типам, а не только к недостаче.
- Проведение (`adjustment.service.js#post`) — одна транзакция, каждая строка
  создаёт ровно одно движение склада и одно событие экземпляра
  (`eventType: 'adjustment'`, `documentType: 'stock_adjustment'`):
  `surplus` создаёт новый экземпляр (`generateInventoryNumbers` одним запросом
  на все surplus-строки документа, не в цикле) и связывает его `instanceId` с
  породившей строкой; `shortage` списывает экземпляр (`status='write_off'`,
  как у Списания) при обязательной проверке `status==='in_stock'`; `relocate`
  меняет `warehouseId`; `condition` меняет `condition` без изменения склада —
  движение для него создаётся тоже (тот же `fromWarehouseId`/`toWarehouseId`),
  как аудиторский след, что документ физически затронул экземпляр.
- `POST /adjustments/documents/from-inventory/:inventoryDocumentId` —
  создание черновика по завершённой инвентаризации: одна транзакция создаёт
  шапку (склад/дата берутся из инвентаризации) и строки `shortage` по каждой
  неподтверждённой позиции снимка, с `inventoryDocumentId` на каждой строке
  (не на шапке — документ может сочетать строки из инвентаризации и
  добавленные вручную). Известное ограничение: сама инвентаризация не
  помечается как "по ней уже создана корректировка", поэтому повторный вызов
  того же эндпоинта после первой корректировки создаст ещё один черновик с
  теми же (уже списанными) позициями — попытка провести его получит `400` на
  каждой строке. В реальной эксплуатации создаётся сразу после завершения
  сверки, повторный вызов — не ожидаемый сценарий.
- Frontend: `client/src/features/adjustments/`, `client/src/pages/adjustments/`
  — форма строки одна (`EntityFormModal` + `lineFields` с `hiddenWhen` по
  `adjustmentType`, тот же паттерн, что у `receiving`), а не 4 отдельные
  модалки. Кнопка "Создать корректировку" на завершённой Инвентаризации

  `adjustments.manage` и `summary.missing > 0`.
- `server/src/tests/adjustments.test.js` — один документ на все 4 типа строк

  экземпляру), плюс отдельный сценарий "черновик из инвентаризации" (создание

  неподтверждёнными позициями снимка, повторное проведение — `409`).
- Найден и исправлен через живую Playwright-проверку баг фронтенда:

```

- карточка экземпляра, модель, размер и инвентарный номер;

  upd/
  shared/
```

Для каждой формы должны быть отдельные builder, mapper, шаблон и тест. Общие
денежные, исторические и форматирующие функции размещаются в `shared`.

## Задача 19. Конструктор макетов Excel-актов

Статус: **Не начато**.

### Цель

Позволить администратору изменять внешний вид Excel-актов без правки кода:
выравнивать строки и ячейки, менять размеры, оформление и параметры печати,
не затрагивая источники данных и правила денежных расчётов.

Конструктор отвечает только за макет. Состав данных, отбор работников и
одежды, цены, НДС, формулы и итоги остаются в backend соответствующей
печатной формы.

### Первый этап: менеджер Excel-шаблонов

- [ ] Выбрать тип печатной формы.
- [ ] Скачать активный шаблон `.xlsx`.
- [ ] Загрузить изменённый шаблон.
- [ ] Проверить шаблон до сохранения.
- [ ] Сформировать предпросмотр на тестовых или выбранных данных.
- [ ] Сравнить результат в Excel и PDF.
- [ ] Сохранить новую версию без перезаписи предыдущей.
- [ ] Активировать выбранную версию.
- [ ] Вернуться к любой предыдущей версии.

Редактирование самого файла на первом этапе выполняется в обычном Microsoft
Excel или совместимом редакторе. В программе реализуется безопасное хранение,
проверка, предпросмотр, версионирование и активация макетов.

### Поддерживаемое оформление

- ширина столбцов и высота строк;
- горизонтальное и вертикальное выравнивание;
- перенос текста;
- объединение ячеек;
- шрифты, границы и заливки;
- числовые форматы;
- логотип и статические изображения;
- книжная или альбомная ориентация;
- поля страницы, масштаб и область печати;
- повторяемые строки заголовка таблицы;
- расположение реквизитов, подписей и итогов.

### Разметка шаблона

Отказаться от жёсткой привязки генератора к координатам вроде `A34` и
`dataStart: 42`. Использовать именованные области Excel или проверяемые
маркеры:

```text
{{DPO_NAME}}
{{PERIOD}}
{{CONTRACT_NUMBER}}
{{TABLE_START}}
{{EMPLOYEE_NAME}}
{{MODEL_NAME}}
{{INVENTORY_NUMBER}}
{{PRICE}}
{{TOTAL}}
{{TABLE_END}}
{{GRAND_TOTAL}}
```

Повторяемая строка таблицы должна определяться отдельной именованной областью.
Генератор копирует её стиль, формулы и объединения для нужного количества
строк, после чего автоматически сдвигает итоговый и подписной блоки.

### Модель хранения

Добавить версионируемую сущность шаблона со следующими данными:

- тип печатной формы;
- номер версии;
- имя исходного файла;
- контрольная сумма файла;
- дата загрузки и пользователь;
- дата активации;
- признак активной версии;
- результат последней проверки;
- комментарий к версии.

Старый файл при загрузке новой версии не удалять. В журнале сформированного
акта сохранять точную версию использованного шаблона.

### Проверка безопасности и совместимости

- [ ] Принимать только `.xlsx` установленного ограничения размера.
- [ ] Запрещать макросы, внешние ссылки и исполняемое содержимое.
- [ ] Проверять наличие всех обязательных именованных областей и маркеров.
- [ ] Проверять единственность повторяемой области таблицы.
- [ ] Проверять корректность объединений и отсутствие их пересечения.
- [ ] Проверять формулы итогов и допустимые поля подстановки.
- [ ] Не позволять шаблону менять рассчитанные backend значения.
- [ ] Не активировать шаблон, если Excel или PDF не может быть сформирован.
- [ ] Ограничить загрузку и активацию отдельным правом администратора.

Файлы шаблонов хранить на локальном сервере приложения с резервным
копированием по правилам задачи 16. Метаданные и историю версий хранить в БД.

### Второй этап: визуальная настройка в браузере

После стабилизации менеджера шаблонов добавить упрощённый редактор, а не
полный аналог Excel:

- изменение ширины столбцов и высоты строк перетаскиванием;
- выравнивание, перенос, шрифт, границы и заливка;
- объединение и разъединение разрешённых ячеек;
- настройки страницы и области печати;
- размещение разрешённых полей из панели данных;
- предпросмотр Excel/PDF до сохранения версии.

### Тесты

- [ ] Изменение ширины столбца и высоты строки сохраняется в Excel и PDF.
- [ ] Перенос текста и объединения не ломаются при 0, 1 и 100 строках акта.
- [ ] Заголовок и подписи правильно сдвигаются при расширении таблицы.
- [ ] Шаблон без обязательного маркера отклоняется с понятной ошибкой.
- [ ] Макрос или внешняя ссылка отклоняется.
- [ ] Новая версия не изменяет предыдущую.
- [ ] Откат возвращает выбранный макет.
- [ ] Пользователь без права администратора не может загрузить или
      активировать шаблон.
- [ ] Суммы одного акта совпадают при использовании разных макетов.

### Критерий готовности

Администратор может скачать шаблон, выровнять и оформить его в Excel,
загрузить обратно, проверить предпросмотр, активировать и при необходимости
откатить версию. Изменение макета не влияет на строки данных и суммы акта, а
результат одинаково корректно отображается в Excel и PDF.
