## Автономность

Раздел 16 `PROJECT_SPECIFICATION.md` уже даёт разрешение не спрашивать
подтверждения для безопасных команд, npm install/uninstall, создания

потенциально разрушительными действиями (массовое удаление кода, изменение
схемы БД без миграции, удаление данных, изменение истории Git). Это уже
подтверждено на практике за 11 этапов работы — просто продолжай в том же
духе, не переспрашивая "начать с X?". Git push тоже подтверждён явно
пользователем как штатное действие (не разово) — можно пушить после
коммита, не переспрашивая каждый раз, но по-прежнему не молча (сообщать,
что запушено). Исключение из этого исключения см. в "Текущий статус"
ниже — в конце сессии Этапа 11 пользователь явно попросил не коммитить

не отмена общего разрешения на будущее; если рабочее дерево снова окажется
с незакоммиченными изменениями в начале твоей сессии и явного запрета не
было — коммить как обычно.

## ДЕПЛОЙ — в процессе, оборвался по контексту (31.07.2026) — ПРОДОЛЖИ ОТСЮДА

### Согласовано с пользователем (не переспрашивать заново)

1. **Способ**: нативно на Windows, без Docker (Docker Desktop не установлен,
   пользователь явно попросил "просто запустить сервис" — не тратить время на

2. **Доступ**: пользователь сначала просил Tailscale, потом отказался
   ("надо постоянно дёргать", хотя это неверное понимание — Tailscale работает

   Cloudflare Tunnel** ("нужен публичный для демонстрации"), без своего домена

   без аккаунта Cloudflare. **Важно понимать ограничение**, которое пока не
   успел проговорить с пользователем явно: URL вида
   `https://<случайные-слова>.trycloudflare.com` **меняется при каждом
   перезапуске** процесса `cloudflared` (в т.ч. при перезагрузке ПК) — это
   ограничение бесплатного Quick Tunnel без домена, не баг настройки. Если
   пользователь настаивает на неизменной ссылке — единственный способ решить
   это в лоб: завести домен и настроить именованный tunnel (пользователь
   сказал "домена нет, давайте просто быстро" — т.е. согласился на этот
   компромисс, но стоит перепроверить, знает ли он про смену URL при
   перезагрузке).
3. **Позже пользователь уточнил контекст** ("так как это моя разработка, я

  `curl --data-binary @file.json` / `psql -f file.sql`, либо гонять кириллицу
  только через stdin (пайпы это не ломает), либо просто использовать
  латинские тестовые имена (`pwwhdocs<timestamp>` и т.п.) — так делали
  Playwright-проверки в нескольких сессиях подряд. Сами данные в БД/
  приложении не повреждаются — проблема только в этом одном инструменте
  тестирования.
- Инструменты Read/Write/Edit иногда не видят файл, который только что сами
  создали в этой же кириллической папке (`2-этаж Ржд`) — ошибка "File does
  not exist" сразу после успешного создания, притом что повторный вызов того
  же инструмента с тем же путём затем срабатывает. Природа не установлена
  окончательно (подозрение на рассинхронизацию с OneDrive, который часто
  делает Known Folder Move для `Desktop` на Windows, либо на путаницу
  Unicode-эквивалентных форм написания кириллицы при повторном наборе пути
  моделью) — не является багом кода проекта. Что помогает: (1) для новых
  файлов использовать `cat > relative/path <<'EOF' ... EOF` через Bash с
  относительным путём (без кириллицы вообще, если `cd` в корень проекта уже
  выполнен) — надёжнее, чем Write/Edit с абсолютным путём; (2) для правки
  существующих файлов — `perl -0pi -e` или `sed` через Bash вместо Edit;
  (3) если Read/Write/Edit всё же нужны — просто повторить вызов, обычно
  срабатывает со второго раза; (4) после Bash-правок всегда проверять
  `cat`/`grep` результат — не доверять только сообщению об успехе.
