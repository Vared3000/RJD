# Запуск ERP только в локальной сети

Целевая схема публикует на сервере только HTTP-порт frontend. PostgreSQL и
backend не имеют портов на хосте: frontend передаёт запросы `/api/*` и
`/health` во внутренний backend через Docker-сеть.

## 1. Закрепить адрес сервера

Рекомендуемый вариант — зарезервировать постоянный IPv4 для сервера на
DHCP-сервере/маршрутизаторе. Альтернатива — статический адрес, настроенный
сетевым администратором. Адрес не должен меняться после перезагрузки.

Если в организации есть локальный DNS, создайте имя, например
`workwear.company.local`, указывающее на этот IPv4. Не создавайте публичную
DNS-запись и переадресацию порта на интернет-маршрутизаторе.

## 2. Настроить `.env`

Пример для сервера `192.168.1.20` и подсети `192.168.1.0/24`:

```dotenv
LAN_BIND_ADDRESS=192.168.1.20
LAN_SUBNET=192.168.1.0/24
CLIENT_ORIGIN=http://192.168.1.20
```

Если используется локальное DNS-имя, в `CLIENT_ORIGIN` указывается имя, но
`LAN_BIND_ADDRESS` всё равно должен содержать постоянный IPv4 сервера.

Проверьте остальные пароли и JWT-секреты по `.env.example`. PostgreSQL в
`DATABASE_URL` должен ссылаться на сервис `postgres` только внутри Compose;
готовый `docker-compose.yml` формирует эту строку сам.

## 3. Запустить контейнеры

```powershell
docker compose config
docker compose up -d --build
docker compose ps
```

В выводе `docker compose ps` опубликован только frontend:
`LAN_BIND_ADDRESS:80`. У `postgres` и `server` не должно быть опубликованных
портов `5432` и `4000`.

Если на Windows уже установлен отдельный PostgreSQL, он не нужен для
эксплуатационного Compose. Проверьте `netstat -ano -p TCP`: порт `5432` не
должен слушать `0.0.0.0` или LAN-IP. Остановите ненужную службу либо задайте
ей `listen_addresses = 'localhost'`; `test-lan-mode.ps1` считает внешний
listener `5432` ошибкой.

Проверка на сервере:

```powershell
Invoke-RestMethod http://192.168.1.20/health
```

Ожидаемый статус — `ok`.

## 4. Ограничить Windows Firewall

Откройте PowerShell от имени администратора и выполните:

```powershell
.\deploy\configure-lan-firewall.ps1 -LanSubnet 192.168.1.0/24
```

Скрипт создаёт правило только для TCP 80, профилей Domain/Private и указанной
подсети. Если он предупреждает о других широких разрешающих правилах для
порта 80, их нужно проверить вручную: скрипт не удаляет чужие правила.

Не открывайте во входящих правилах порты `4000` и `5432`.

## 5. Приёмочная проверка

На сервере от имени администратора:

```powershell
.\deploy\test-lan-mode.ps1 `
  -LanAddress 192.168.1.20 `
  -LanSubnet 192.168.1.0/24
```

Затем проверьте с двух рабочих компьютеров локальной сети:

1. открывается `http://192.168.1.20` или локальное DNS-имя;
2. выполняются вход, открытие списка работников и формирование отчёта;
3. после перезагрузки сервера адрес не изменился;
4. порты `4000` и `5432` недоступны через `Test-NetConnection`;
5. на маршрутизаторе отсутствует port forwarding для порта 80 этого сервера.

Если правила предприятия разрешают контроль с внешней сети, отдельно
проверьте, что публичный адрес организации не открывает ERP. Для работы самой
программы доступ к интернету не требуется.

## Что удалено из прежней схемы

Cloudflare Quick Tunnel и его автозагрузка больше не используются. Публикация
через Tailscale также не нужна: Compose слушает только `LAN_BIND_ADDRESS`, а не
виртуальные сетевые интерфейсы.

При обычном HTTP внутри доверенной LAN cookie сессии остаётся `httpOnly` и
`SameSite=Lax`, но не получает флаг `Secure`. Если организация предоставляет
локальный TLS-сертификат, укажите `https://...` в `CLIENT_ORIGIN` и завершайте
TLS на корпоративном reverse proxy — тогда приложение автоматически включает
`Secure` для cookie.
